# Binding decision — test spawn sites migrate through the real chokepoint

**Decided by Tom, 2026-07-27 ~21:05 EDT.** Must be written into
`docs/superpowers/specs/2026-07-27-m1.13-git-process-policy-design.md` before
implementation starts.

## The decision

All ~42 test-module git spawn sites migrate to the same chokepoint the 9
production sites use. They are **not** exempted.

His reasoning, verbatim: *"I'd rather pay the mechanical cost now so the tests
actually exercise the production path, instead of having a false sense of
coverage."*

## Why this is the right call, stated so a later session does not undo it

A test suite that spawns git directly is not testing the thing that ships. Every
invariant the chokepoint enforces — env_clear plus allowlist, the config-scope
suppression, stdin nulling, the timeout, the hooks pin, the cgroup placement —
is invisible to a test that bypasses it. Worse, such a suite passes *because* it
bypasses them: a bug in the chokepoint's env policy would be undetectable by 42
tests that never touch the chokepoint. That is the definition of false coverage,
and it is exactly the failure mode this issue exists to prevent.

There is a second, subtler payoff. Migrating the tests forces the chokepoint's
API to be usable in the shapes tests need (fixture setup, seeded repos,
deliberate failure injection). An API that only production can use comfortably
is an API that will get bypassed the first time someone writes a test in a
hurry.

## What the design must now state explicitly

1. **Scope**: the chokepoint's enforcement mechanism (I2) covers test modules
   too. The "no bypassing call site" invariant is repo-wide, not
   production-only. If the enforcement is a grep-the-tree test or a clippy
   `disallowed-methods` lint, its scope must include `#[cfg(test)]` blocks.
2. **Fixture-setup exemption, if any.** Some test spawns are *arranging* a
   repository (`git init`, seeding commits, `git config user.email`) rather than
   exercising git-vista's behaviour. Decide deliberately whether those go
   through the chokepoint too. Argument for: uniformity, and seeding under the
   real env policy proves the policy does not break ordinary repo setup.
   Argument against: fixtures deliberately need things the policy forbids (e.g.
   setting identity via config rather than `-c`). **Whichever is chosen, the
   design must name the rule and the escape hatch must be a single, named,
   greppable helper — not an ad-hoc `Command::new` scattered through the
   suites.**
3. **The migration is part of #66's definition of done**, not a follow-up. A
   deferred migration never happens.

## Estimate impact — call this out honestly

This materially enlarges #66:

- ~42 call sites across at least `planner/{contract,coordination,lifecycle}_suite.rs`,
  `git_cmd.rs`, `durable.rs`, `journal.rs`, `state.rs`, `coordinator.rs`,
  `history.rs` (both crates).
- Mechanical, but not trivially so: test spawns use varied shapes (`std::process`
  vs `tokio::process`, `.output()` vs `.status()` vs piped `.spawn()`), and the
  chokepoint is async while several test helpers are sync.
- **The sync/async mismatch is the real cost.** `crates/git-vista-git/src/history.rs`
  test helpers use `std::process::Command` synchronously. Routing them through an
  async chokepoint means either a blocking bridge, a sync variant of the
  chokepoint, or converting those helpers to async. That decision needs making
  in the design, not discovered mid-migration.
- Expect the migration to surface latent test assumptions — e.g. a test that
  silently depended on inherited env, or on a hook firing.

**This is well-suited to delegation** (bounded, mechanical, high-volume,
verifiable by `./dev gate`), but only AFTER the chokepoint exists and its API is
stable. Sequencing: Max builds the chokepoint and migrates the 9 production
sites; the ~42 test sites then become a clean delegated task with an unambiguous
acceptance criterion.
