# M1.13 — cgroup containment: what is proven, and what is not (#66)

- **Date:** 2026-07-27
- **Host:** tom-hp-headless, cgroup v2 (`nsdelegate,memory_recursiveprot`), unprivileged user `tom` (uid 1000)
- **Purpose:** the v3 design makes containment the load-bearing invariant. This
  records what was empirically established about it, including a real gap.

## Summary

Containment holds against ordinary process behaviour — forking, exec, and
`setsid` detachment. It does **not** currently hold against a process that
deliberately walks itself out of its cgroup, and the escape-proof construction
the design prescribes could not be made to work on this host in several attempts.

This is a genuine limitation, not a theoretical one. It is recorded here so the
design states a guarantee it can actually keep.

## What is proven to hold

**Descendants inherit the cgroup.** A process spawned inside a leaf cgroup, and
anything it forks or execs, remains a member. `setsid` does not escape it — this
is why cgroups were chosen over process groups in the first place, after round-1
refutation showed `setsid` defeats `killpg`.

**`cgroup.kill` reaches the whole subtree**, including processes that have
re-parented to init. This is the property that makes bounded cancellation
possible at all.

## What is proven NOT to hold

**Upward escape succeeds in the naive construction.** Tested directly:

```
leaf:   /user.slice/user-1000.slice/user@1000.service/<scope>/gvtest-leaf
action: echo <pid> > <parent>/cgroup.procs
result: SUCCEEDED — process is now in the parent, outside the leaf that
        cgroup.kill would target
```

The pid's own cgroup is trivially discoverable via `/proc/self/cgroup`, so this
is a few lines of shell in a hostile hook, not an exotic attack.

The reason it succeeds: the parent's `cgroup.subtree_control` is **empty**. A
cgroup that delegates no controller to its children is permitted to hold
processes directly, so the kernel has no reason to refuse the write. File
ownership is not the control — the "no internal process" rule is.

## Why the prescribed fix did not work here

The design's remedy is to make the spawn parent a **non-leaf** by enabling a
controller on it (`pids` suffices), after which cgroup v2 refuses direct process
membership regardless of ownership. That mechanism is real — verified two levels
up at `user@1000.service`, where the identical write is refused with
`Permission denied`.

Getting there on this host proved harder than the design assumes. Three attempts:

| Attempt | Result |
|---|---|
| `systemd-run --user --scope -p Delegate=pids` | `subtree_control` came back empty; escape still succeeded |
| `systemd-run --user --unit=… -p Delegate=yes`, enable `+pids` on the service cgroup itself | `+pids` enabled, but then moving a process *into* a leaf failed with `Operation not supported` — the service cgroup held the supervisor process, so enabling subtree_control put it in the violating "internal process" state |
| Same, but create `gv-spawns/` as a child and enable `+pids` on it | `No such file or directory` — a controller cannot be enabled on a child unless the parent already delegates it downward |

The correct topology follows from those failures: the supervisor must first move
**itself** into a sibling leaf so the service cgroup holds no processes, only
then can it delegate `+pids` downward to `gv-spawns/`. Attempting that
self-move returned `Invalid argument` and was not resolved before this note was
written.

**This is a "not yet achieved", not a "proven impossible".** The mechanism is
sound and kernel-enforced; the remaining problem is finding the exact cgroup
topology and delegation sequence that systemd's user manager permits. That is
implementation work.

## What the design must therefore say

1. **State the guarantee honestly.** Containment bounds runaway, chatty and
   detaching processes — which covers accidental cases and most hostile ones. It
   does not currently bound a process that deliberately migrates upward.
2. **The startup probe must test escape, not just creation.** Checking "can I
   create a cgroup and write `cgroup.kill`" is insufficient and gave a false
   sense of safety earlier in this session. The probe must attempt an actual
   upward move from a leaf and report degraded mode, loudly, when it succeeds.
3. **Degraded mode must be visible**, not silent. A containment guarantee that
   has quietly downgraded itself is worse than a documented partial one, because
   the design's other decisions lean on it.

## Correction to an earlier claim in this session

An earlier check established that unprivileged cgroup creation and
`cgroup.kill` both work on this host, and that was reported as clearing the
feasibility risk for containment. That was too broad: it verified cgroups can be
**created and killed**, never that a process cannot **leave** one. It can. The
conclusion stands corrected here rather than being quietly dropped.
