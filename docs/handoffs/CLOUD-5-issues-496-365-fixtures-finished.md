## What was actually run here

Everything in this section was executed in a **cloud session on this
repository**, on commit `a21c64a`, not inferred. It is here because #365 has
sat open since 2026-08-08 on a feasibility question that takes one minute to
answer.

**1. Git 2.32.0 builds and runs in a cloud container.** The tarball mirrors are
blocked by the agent proxy — `mirrors.edge.kernel.org` answers `403` to
`CONNECT`, and so does `codeload.github.com` — but `git clone` against
`github.com` works, because git traffic is routed through the proxy's own
config injection:

```sh
git ls-remote --tags https://github.com/git/git v2.32.0
# b7e68c41d92146de98ec5f433e1b123c4df2ac5a  refs/tags/v2.32.0
```

So the source route is a shallow clone, not a tarball fetch:

```sh
git clone --depth 1 -b v2.32.0 https://github.com/git/git "$SRC"
make -C "$SRC" -j"$(nproc)" prefix="$PREFIX" \
  NO_GETTEXT=1 NO_TCLTK=1 NO_CURL=1 NO_EXPAT=1 NO_PERL=1 NO_PYTHON=1 install
"$PREFIX/bin/git" --version        # -> git version 2.32.0
```

`NO_GETTEXT` and `NO_TCLTK` are not optional here: `msgfmt` and `tclsh` are
absent from this image. `NO_CURL`/`NO_EXPAT` drop the HTTP transport, which
`git status` does not need and which saves the dependency hunt. Clone plus
build took **about a minute** on four cores (195 MB of source, a 58 MB
prefix) — small enough to run in CI on every push, though see the caching note
below.

**2. All seven conflict `XY` combinations are producible by real git, in
exactly two merges.** This is the part of #365's acceptance list most likely to
be quietly dropped, so it is settled in advance. A rename/rename(1to2) merge
gives three of them at once:

```
u DD ... f.txt
u AU ... main-name.txt
u UA ... side-name.txt
```

— from `base` → one branch does `git mv f.txt side-name.txt`, the other does
`git mv f.txt main-name.txt`, then merge. `DD` in particular does **not**
require both sides to plainly delete the file; it falls out of the rename
conflict. The other four come from one ordinary merge in which both sides
modify one path, both add another, and each deletes one the other edited:

```
AA both-add.txt
UU both-mod.txt
UD they-del.txt
DU we-del.txt
```

Two shapes, seven kinds, no gaps. Both recipes were run on git 2.43.0 and the
output above is verbatim.

**3. The answer #365 is looking for is almost certainly "no difference" — and
that is the trap.** Both repositories above were read with 2.43.0 and with the
freshly built 2.32.0:

```
git status --porcelain=v2 --branch -z              → byte-identical
git status --porcelain=v2 --branch -z --ignored    → byte-identical
```

Byte-identical, both shapes, both flag sets. This matches what `status.rs`
already reasons about at lines 268-272 — porcelain v2 has not changed shape
since 2.11. **So a comparison harness that silently never invoked the 2.32
binary would pass exactly as loudly as a correct one.** A4 exists because of
this and is the single most important criterion in this document; the section
"Making the green mean something" below is not advice.

## Part one — #496: the last JavaScript builder

### What is actually there today

`ci/browser/fixture.mjs` is 260 lines. Lines 1-210 are the post-#448 file: a
`build(shape, root)` helper that spawns `target/debug/gv-fixture`, plus thin
wrappers returning each fixture's metadata. **Lines 211-260 are
`buildStashFixture`, which still builds its repository from JavaScript** —
`rmSync`, `mkdirSync`, `writeFileSync`, and `execFileSync('git', [...IDENT,
...])`.

Two things in that file carry a comment marking them as on loan to those fifty
lines:

- **line 29** — `import { existsSync, mkdirSync, rmSync, writeFileSync } from 'node:fs'`.
  Three of those four are the loan; `existsSync` is not (see below).
- **lines 41-46** — the `IDENT` array. All of it is the loan, and it goes.

### The issue is wrong about `node:fs`

#496's acceptance criterion 2 reads: *"`ci/browser/fixture.mjs` needs neither
`node:fs` nor `IDENT` afterwards, and both are removed with the builder rather
than left behind."* Half of that is not achievable, and a session that treats
it as a checklist will either delete a live call or report a criterion met that
is not.

`existsSync` is called at **line 62**, inside `build()` — the guard that turns a
missing `gv-fixture` binary into a loud error naming the `cargo build` command
instead of a spec failing against an empty directory. `git log -L 62,62` puts
that line in commit `539ba7c`, *"refactor(#448): the browser harness builds its
fixtures by invoking Rust"*. It is the catalogue's own code, not #490's. And
#490's version of this file imported exactly `{ mkdirSync, rmSync, writeFileSync }`
— no `existsSync` — which confirms it from the other side.

So the correct end state is:

```js
import { existsSync } from 'node:fs'     // stays: build()'s missing-binary guard
```

`IDENT` goes entirely; the `node:fs` import narrows. Say this in the PR body
rather than silently satisfying three quarters of a criterion, and do not delete
the guard to make the sentence true — the guard is the better thing.

The issue's account of how this happened is correct and was checked against
history: #448 (PR #491) and #77 (PR #490) both touched this file, neither
touched the other's lines, git merged them without a conflict, and the result
called `rmSync` and spread `IDENT` with neither in scope. It surfaced only in
`globalSetup`, in a leg CI does not run. Commit `8504ca8` restored both with
comments marking them as on loan.

### The job

Add a seventh shape. `crates/git-vista-fixtures/src/browser.rs` holds six
today, listed in the `SHAPES` table at **line 559**:

```rust
pub const SHAPES: &[(&str, Builder)] = &[
    ("main", main_fixture),
    ("conflict", conflict_fixture),
    ("non-text-conflict", non_text_conflict_fixture),
    ("editor", editor_fixture),
    ("broken-head", broken_head_fixture),
    ("interleaved-wip", interleaved_wip_fixture),
];
```

`("stash", stash_fixture)` joins it; `gv-fixture` needs no change, because it
dispatches off that table. `buildStashFixture` in `fixture.mjs` collapses to
`build('stash', root)` plus the metadata object it already returns.

### Four things that will bite

**The doc comment is the deliverable, not the port.** Every shape in this crate
states *what is wrong*, *what git put on disk*, and *why it matters* — that is
the whole argument of ADR 0076, and a shape moved in with a one-line comment
fails the acceptance the crate exists for. The JavaScript already carries most
of the reasoning (why `stash@{0}` is the conflicting one, why the two message
forms are both present, why the untracked file is never stashed); it is good
material and should be carried over and deepened, not paraphrased away. The
one genuinely interesting fact to explain: `git stash` with no `-m` writes
`WIP on main: <sha> <subject>` and `git stash push -m` does not, which is why
one entry renders with an "auto" pill and the other does not — the drawer is
telling two *git message formats* apart, not two user intentions.

**`fresh()` adds a local config the JavaScript never wrote.**
`browser.rs`'s `fresh()` calls `git::init_as`, and `init_as`
(`git.rs`, near the end) runs `git config user.email` and `git config
user.name` into the fixture after `git init`. `buildStashFixture` today passes
identity **only** as `-c` flags and leaves the repo's config empty. So the
moved shape gains a local identity. That is almost certainly an improvement —
`git.rs`'s module doc explains it exists so suites can keep committing into a
fixture afterwards — but it *is* a difference, it is the kind of difference
that makes a spec pass for a new reason, and it should be named in the PR body
rather than discovered later. Check that no stash spec asserts on config or on
a commit author.

**The metadata is stated in three places and will drift.** After the move,
`collision.txt` and `'will not apply cleanly'` are named by the Rust builder,
by `fixture.mjs`'s return object, and again by
`ci/browser/tests/helpers.mjs` (lines 192 and 194, `CONFLICTING_SUBJECT` and
`CONFLICTING_PATH`), which re-declares them as literals rather than importing
them. Follow the precedent already in the file: `WIP_RUN_COUNT`,
`TWIN_CHECKPOINTS`, `BIG_FILE_LINES` and `MULTI_HUNK_COUNT` are all Rust
constants with a JavaScript mirror carrying a "must stay in sync with
`browser::X`" comment. Do the same for the stash facts. Having `helpers.mjs`
import from `fixture.mjs` instead of re-declaring is a genuine improvement and
is inside the fence — but it is the only thing in `helpers.mjs` you may touch.

**You cannot run the acceptance test.** The issue's criterion 3 is
"`ci/browser/run.sh` is green on Tom's box — the only place it can run", and
that is literally true: `run.sh` needs `unshare --net` (which works here) *and*
a server that will start, and per ADR 0029 the server refuses to run below the
strict sandbox tier. **Landlock was probed directly in this session —
`landlock_create_ruleset` returns `-1`** — so the tier is unavailable and the
gate cannot be called green from a cloud session. Say so plainly; do not
report criterion 3 as met.

### How to verify it anyway

ADR 0076 has the answer, and it is better than "I read the diff": each
JavaScript builder was executed under Node beside its Rust replacement and the
two repositories were compared on **full git state — commit graph, index
including conflict stages, working-tree contents, untracked files, `HEAD` and
`MERGE_HEAD`**. That is a real equivalence proof, and this shape has extra
state to compare: `git stash list`, and each entry's tree.

One correction to how that was done last time, found while writing this: **that
harness was never committed.** Nothing in the tree resembles it, so the
strongest evidence #448 produced cannot be re-run by anyone. Commit yours —
`ci/` is inside the fence — even if it is fifty throwaway lines. A proof that
exists only in a PR body is a proof with a half-life.

Delete the JavaScript builder in the *same commit* that adds the Rust one, so
the equivalence check is a thing you ran, not a thing the tree still permits.

## Part two — #365: exercising the floor instead of asserting it

### The gap is real and the issue cites it correctly

Verified rather than trusted, since the citation is the whole basis of the
issue: **`crates/git-vista-protocol/src/status.rs` lines 263-276** say exactly
what #365 says they say. The comment records that every record shape was
captured from a real `git status --porcelain=v2 --branch -z` on **2.43.0**,
that the documented floor is **2.32**, that porcelain v2 has not changed shape
since 2.11 — and then refuses to round that into a claim:

> *"this parser has only been exercised against 2.43.0 — a single version, not
> the floor itself. That is a real gap against #68's ... criterion, named here
> rather than silently claimed satisfied"*

`docs/SUPPORTED_VERSIONS.md` sets the floor at 2.32 and explains why
(`GIT_CONFIG_GLOBAL`, added June 2021). The CI step at
`.github/workflows/ci.yml:153`, "Git version meets the documented floor",
parses `## Git: X.Y or later` out of that file and fails a runner *below* the
floor — it does not provision or test the floor. Every clause of the issue's
"Gap" section holds.

### The parser's tests are all literals, and that is fine

`status.rs` has 15 `#[test]`s; **12 of them drive `parse_porcelain_v2_z`**
(the other three round-trip the DTO through serde and never touch the parser),
and every one of the 12 feeds it a hand-written byte string. They contain oids
like `6666666666666666666666666666666666666666`. They are good tests of the
parser and they are not evidence about any git version at all, because no git
ran. Nothing here is wrong with them; #365 is asking for a **second,
different** kind of test beside them, not a replacement.

The expected side of that test already exists in a usable form.
`crates/git-vista-protocol/tests/status_golden.rs` builds one `WorktreeStatus`
covering every `StatusEntry` variant, every `ChangeSides` shape, every
`ConflictKind`, and both submodule states — and its second test,
`golden_set_covers_every_entry_kind_and_conflict_kind`, *proves* that coverage
is exhaustive by round-tripping through serde and comparing tag sets. Reuse
that idea for the new leg's expectations: an enumerated set, with a test that
fails when a variant is missing, beats a list someone maintains by hand.

### Shape of the work

**1. The battery belongs in the catalogue.** This is why the two issues share a
document. #365 says "generate real worktree-status fixture repositories", and
this repository now has exactly one right place for that:
`git-vista-fixtures`. Add `status_battery()` (or two shapes — the conflict
recipes above are naturally two repositories) with the crate's usual essay-grade
docs. Do **not** build these repositories inside the test file; that is the
twenty-`seeded_repo()` mistake #448 just finished paying off.

**2. Where the test lives.** A test that spawns git cannot live in
`status.rs`, whose module doc opens by calling `parse_porcelain_v2_z` "a **pure
function** over bytes: no git process spawn". An integration test —
`crates/git-vista-protocol/tests/status_floor.rs` — keeps that claim true: the
function stays pure, the test around it is allowed to be impure, and
`git-vista-fixtures` goes in `[dev-dependencies]` exactly as the server's
suites already take it (`crates/git-vista-server/Cargo.toml`,
`git-vista-fixtures = { workspace = true }`; the workspace row is at the root
`Cargo.toml` line 45 and already says "a dev-dependency only").

This does not endanger the crate's purity claim, and the precedent is in the
file you would be editing: `git-vista-protocol`'s own `[dev-dependencies]`
already carries `git-vista-core` under the comment *"Never a non-dev
dependency — this crate must stay pure and wasm-safe, and git-vista-core is
neither."* A dev-dependency is not built for the wasm target by the Trunk
frontend build, and `git-vista-fixtures` depends on nothing but `tempfile`, so
there is no cycle. Write the same kind of comment beside your row.

**Check before you worry about the argv boundary.** The server's
`argv_boundary.rs` tests scan for `Command::new` and enforce an allowlist, and
that guard is real — but it is pointed at exactly two crate roots,
`git-vista-server` and its sibling `git-vista-git` (lines 491 and 562). A spawn
in `git-vista-fixtures` or in a protocol integration test does not trip it.
**Do not add an allowlist entry for one.** The companion test
`every_allowlist_entry_names_a_live_spawn_site` fails on entries that name no
live spawn site, and it has already caught one dead entry; a speculative row
would go red for a reason no reader could act on.

**3. Provision the binary, and fail without it.** A2 is the criterion the issue
puts most weight on — "make the 2.32 leg mandatory rather than silently falling
back to the runner's ambient Git" — and it is where this leg is easiest to
build wrong. The binary's path comes from an environment variable
(`GV_GIT_232`, say). If it is unset or missing, the test **fails**; it does not
`#[ignore]` itself, does not skip, and does not fall back to `git` on `PATH`. A
skipped test reports the same green as a passing one, which is the failure mode
this repository has now written down six times.

The floor number itself must keep coming from `docs/SUPPORTED_VERSIONS.md`.
That anti-drift pattern is already used twice in `ci.yml` — the version-floor
step at line 153, and *"Dependency exceptions register is honest"* at line 459,
which cross-checks `.cargo/audit.toml` against
`docs/DEPENDENCY_EXCEPTIONS.md` — and duplicating `2.32` into a
build script would break the doc's own claim to be the single source of truth.
Parse it; do not retype it.

For CI: a build takes about a minute, but running it on every push to add a
minute to `core` is worth avoiding. `actions/cache` keyed on the parsed floor
number is the obvious move — a cache miss rebuilds, a hit is instant, and the
key changes automatically if the documented floor ever moves. Decide, and say
what you decided.

**4. Read with both, compare the semantics.** Build each battery repository
**once**, with the ordinary git, then run `git status --porcelain=v2 --branch
-z` over it with both binaries. Building each repository twice would conflate
"the two gits disagree about status" with "the two gits built different
repositories", and the former is the only question here. Parse both streams
through `parse_porcelain_v2_z` and assert each against a **named expected
value**, not merely against each other — two identical wrong answers compare
equal.

**5. `Ignored` needs a decision, and the decision needs saying.** The issue's
acceptance list includes ignored files. Production never asks for them: the
`/api/status/v2` handler runs exactly `["status", "--porcelain=v2",
"--branch", "-z"]` (`crates/git-vista-server/src/handlers/read.rs`, lines
967-972), and no git invocation anywhere in the workspace passes `--ignored`
(every hit of that string is cargo's own test flag). So `StatusEntry::Ignored`
is a variant the parser can produce and the product never sees. Both resolutions are defensible — read the battery a second time
with `--ignored` so the `!` record is exercised against both binaries, or drop
it and record why — but "the acceptance list said ignored so I asserted on an
empty result" is not. Whichever you pick, write it down.

### Making the green mean something

**Expect the comparison to pass on the first run.** It did here, byte for byte,
on every shape and both flag sets. That is the correct outcome and it is also
indistinguishable from a harness that never ran the second binary.

So A4 is not optional and not satisfied by inspection. Concretely:

- Assert the provisioned binary's identity from the binary itself —
  `$GV_GIT_232 --version` must report the documented floor — *before* comparing
  anything. A harness pointed at a copy of 2.43 must go red on that line.
- **Mutation-prove it**, the way #209's closeout proved the rename/copy test:
  point the variable at the ordinary `git`, run the suite, and record that it
  fails. Put that transcript in the PR body. This repository's own history has
  the argument for it — `failure-atlas: caught` against a committed source
  commit — and a comparison test is the single easiest kind of test to write
  vacuously.
- Ask the question the standing rule asks: *what would make this pass while the
  mechanism was broken?* Here the answer is short and specific — an unset
  environment variable, a silent skip, or an expectation derived by calling the
  parser instead of stating the value. Close all three.
