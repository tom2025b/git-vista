# C11 — re-audit of `escape_suite.rs` after the C8 rewrite

**Verdict: the rewrite is not certifiable as proof of production containment.**

Source-only audit; no Cargo command, server operation, port bind, or Git mutation was performed. The five live tests classify as **0 PROVES containment, 4 VACUOUS, 1 UNCERTAIN** under C11's required production-composition standard.

The rewrite materially improves the *executed* A/B branches: it creates real targets, gives `io_uring_setup` a faithful ABI struct, uses a live listener, checks successful blocked-hook commits, and makes the high-bit seccomp check distinguish the kernel result from the filter's `EPERM`. Those improvements do not close the battery's remaining false-green and composition gaps.

## Decisive per-test table

“Sandbox removed” below means Landlock, the Git-Vista seccomp filter, and (for Strict) the bwrap namespace boundary are absent while the same hook/probe and fixture remain. A Rust test that prints `SKIPPED` and returns is green to libtest, so that is a passing path, not a third result state.

| Test | Does it drive the required composition? | Would it pass with the sandbox removed? | Verdict |
|---|---|---|---|

| `the_seccomp_high_bit_denial_is_eperm_not_a_kernel_reject` (`:272-311`) | **No.** It exercises the real fused shim but bypasses production policy/spawning and clears inherited execution-control variables that production retains. | **No.** A bare-Git inside leg repeats the baseline's non-`EPERM` result and fails the `Some(EPERM)` assertion. | **UNCERTAIN** |

## Cross-cutting composition failure

Every sandboxed leg follows this route:

```text
workable(test policy)
  -> commit_sandboxed
  -> shim_cli::launch
  -> sandbox_argv
  -> gv-sandbox
  -> Landlock + seccomp
  -> git hook
```

This is not primitive-in-isolation testing: none of the five tests directly builds a Landlock ruleset, applies seccomp, or executes bwrap. It is nevertheless **not the required production composition**:

- `commit_sandboxed` calls `shim_cli::launch` (`escape_suite.rs:81-91`).
- `launch` calls `sandbox_argv` and constructs its own `std::process::Command` (`shim_cli.rs:85-104`).
- Production instead calls `policy_for_repo` and `sandbox::spawn::command_async` (`git_cmd.rs:127-151`); the production wrapper centralizes argv construction in `spawn.rs:31-74`.
- The test launcher clears the environment down to `PATH` and `HOME` (`shim_cli.rs:85-99`), while production deliberately inherits its environment (`spawn.rs:41-45`, `:54-74`). This is not cosmetic: for inherited command-execution inputs, the security harness is more hardened than the path that ships.
- All five tests use the test-only `workable` policy builder (`shim_cli.rs:34-56`), never `policy_for_repo`.

Consequently, these tests can prove behavior of the fused shim reached through a parallel harness, but cannot prove that the production policy builder and production spawn chokepoint carry the same boundary. That is exactly the layer-versus-composition credit the task forbids.

There is no rescue through the other allowed composition shape. `probe_argv` appends `--self-probe` (`sandbox/mod.rs:507-525`), but the current shim parser has no `--self-probe` arm and rejects unknown flags (`src/bin/gv-sandbox/main.rs:182-224`). None of the five tests uses that path anyway.

Production reachability is narrower still: `policy_for_repo` currently hard-codes `Tier::Network` and `HookMode::Run` (`sandbox/mod.rs:440-467`). The Strict and Blocked test configurations are not production-reachable today.

### Concrete security-relevant divergence: inherited environment

The two launch paths deliberately run opposite environment policies:

```text
escape battery:  env_clear() + PATH=/usr/bin:/bin + HOME=<real home>
production:      inherit the server process environment, minus nothing
```

The shim then applies Landlock and seccomp and only afterward `exec`s literal `git` without clearing the environment (`src/bin/gv-sandbox/main.rs:547-566`). The battery therefore does not exercise production's inherited environment at either the shim or Git boundary.

What remains unproven by all five verdicts:

| Input | Where it can act in production | What C11 establishes |
|---|---|---|
| `LD_PRELOAD` | If effective for the dynamically loaded shim, loader code runs before Rust `main`, hence before `apply_landlock`/`apply_seccomp`. It would normally also have affected the server when that process started unless introduced later. | Stripped from every escape-test launch; pre-policy behavior is untested. |
| `PATH` | The shim path and Strict bwrap path are absolute, but the shim's final `Command::new("git")` resolves `git` using inherited `PATH` after policy installation. | Tests pin `/usr/bin:/bin`; production path selection is untested. |
| `GIT_SSH_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_PROXY_COMMAND` | Consumed by Git for the relevant transport/diff operation after the shim has installed policy. | Stripped by the harness, and the battery only runs commits rather than those operation classes. |
| `GIT_CONFIG_GLOBAL`, other `GIT_CONFIG_*`, `GIT_EXEC_PATH` | Change the configuration/subprograms Git reads or executes after policy installation. | Stripped by the harness; production inheritance is untested. |
| `core.fsmonitor` | **Not an environment variable.** It is a Git configuration command and may be repository-local; Git can invoke it after policy installation. | The environment mismatch is not its cause, but no escape-suite test installs a hostile fsmonitor, so this repository-driven command path is independently unproven. |

This is a **proof gap, not a demonstrated hostile-repository escape** on the live source reviewed. The production server mutates only two fixed Git variables at startup—`GIT_TERMINAL_PROMPT=0` and `GIT_EDITOR=true` (`main.rs:123-132`). The request/protocol paths expose no environment field, no production code copies repository values into `std::env`, the `gv` launcher exports only `GIT_VISTA_*` settings (`gv:478-488`), and the supplied systemd unit has no repository-owned `EnvironmentFile` (`contrib/systemd/git-vista.service:16-23`). A hook child also cannot mutate its parent process environment.

The source audit therefore found **no repository-content-to-server-environment path**. It does not prove that an external shell, service manager, wrapper, or future code cannot supply such values. Finding a repository-controlled route into that parent environment would upgrade this from a composition proof gap to a pre-policy code-execution finding and should supersede the vacuity findings; no such route was found here.

## Per-test reasoning

### 1. `a_hook_reading_an_excluded_secret_is_denied_by_landlock` — VACUOUS

What improved:

- The test creates a present, mode-`0600` sentinel file and the outside hook must print that sentinel (`escape_suite.rs:165-191`). On the exercised branch, the baseline genuinely establishes readability.
- With a cleanly removed sandbox, the inside hook would print the sentinel and fail `:198-202`. The executed branch therefore catches total removal.

Why it still cannot go green as proof:

- If `~/.ssh` is absent, `:159-164` prints `SKIPPED` and returns. Libtest records that as a pass. The sandbox can be absent and this test remains green.
- The inside assertion does **not** check `EACCES`. The hook itself prints `READ_FAIL` for every `cat` failure (`:177-180`), and `:203-207` accepts `"Permission denied" || "READ_FAIL"`. `ENOENT`, an intervening deletion, or any other `cat` failure satisfies it. The declared `EACCES = 13` at `:36` is unused.
- The fixed real-home path is unsafe as a fixture: `std::fs::write` overwrites any existing `~/.ssh/gv-escape-probe-secret`, and the `Drop` cleanup then deletes it (`:165-175`). The sentinel is fixed rather than unique across concurrent runs.
- Even its exercised branch covers only the stripped two-variable environment, not the production inheritance described above.

Minimum repair: use a unique controlled temp tree included as a read grant with a test exclusion beneath it; run a small open/read probe that prints numeric errno; assert outside `Some(0)` plus sentinel and inside exactly `Some(EACCES)` plus no sentinel. Capability absence must not return success in the required security job.

### 2. `a_hook_opening_io_uring_is_denied_by_seccomp_with_eperm` — VACUOUS

What improved:

- The C probe uses `<linux/io_uring.h>` and `struct io_uring_params`, closes a successful ring, and emits numeric errno (`:223-238`).
- When the outside leg returns `Some(0)`, the inside leg requires exactly `Some(EPERM)` (`:239-262`). With the shim removed on that capable host, the inside leg returns zero and the test fails. That executed A/B is strong shim-level evidence.

Why it still cannot go green as proof:

- Every baseline value except `Some(0)`—including `Some(EPERM)` from an outer policy and `None` because the hook/probe never produced output—prints `SKIPPED` and returns success (`:243-248`). The exact restricted-runner condition C8 warned about therefore still produces a green test; it has merely moved from the inside assertion to the baseline gate.
- Current CI runs `cargo test --workspace` without a skip-count or capability-result gate (`.github/workflows/ci.yml:151-152`). The uppercase `SKIPPED:` line has no consumer in the live repository.
- The inside leg still uses the duplicated test launcher rather than production composition.
- The exact `EPERM` A/B never runs with production's inherited environment, so it cannot cover environment-selected Git helpers or pre-policy shim loading.

Minimum repair: make baseline incapability a non-green result in the required sandbox job (or have an external preflight explicitly prevent the job from claiming success), and drive both legs through the production spawn seam.

### 3. `the_seccomp_high_bit_denial_is_eperm_not_a_kernel_reject` — UNCERTAIN

This is the one test that is not vacuous under the removal thought experiment:

- It has no early return.
- It requires a parseable non-`EPERM` outside result and exact `EPERM` inside (`:286-310`).
- The real filter compares the low 32 bits (`seccomp_filter.rs:83-102`) and returns terminal `EPERM` (`:117-128`).
- If the filter is removed, the inside call follows the same kernel path as the outside call and cannot satisfy both assertions.

Three limits prevent a production-containment verdict:

- It bypasses `policy_for_repo` and the production spawn wrapper as described above.
- Its launcher clears inherited execution-control variables, whereas production carries them into the shim and Git.
- The baseline comment promises kernel `EFAULT`, but `:290-297` accepts any parsed value except `EPERM`, including `0`, `ENOSYS`, `EINVAL`, or `EACCES`. The differential is meaningful, but the stated provenance is broader than the assertion.

Verdict: **UNCERTAIN for production containment; strong evidence for the fused shim's high-bit seccomp rule.** Routing it through the production launcher and requiring the documented baseline result would promote it to PROVES.

### 4. `blocked_hooks_are_suppressed_while_the_commit_still_succeeds` — VACUOUS for containment

The rewrite repairs C8's immediate false green. The `--hooks-run` leg requires the marker and a zero commit status; the blocked leg requires marker absence and a zero commit status (`:326-356`). That is a sound functional test of hook suppression.

It is not containment evidence. `sandbox_argv` explicitly supports `Tier::Unsandboxed + HookMode::Blocked` as bare `git -c core.hooksPath=<empty>` (`sandbox/mod.rs:490-499`). Replacing both sandboxed policies with their unsandboxed equivalents preserves the run/blocked distinction and satisfies every assertion with no Landlock, seccomp, or bwrap at all.

Production also constructs only `HookMode::Run` today (`sandbox/mod.rs:451-467`). Keep this as a hook-mode behavior test, but do not count it in the escape battery's containment total.

The test also says nothing about hook/config command discovery under the full production environment because both A/B legs run through the stripped harness.

### 5. `the_strict_tier_hook_cannot_reach_a_live_listener` — VACUOUS

What improved:

- The listener is guaranteed present: bind must succeed, a retained background thread accepts connections, and the outside hook must report `CONNECT errno=0` (`escape_suite.rs:375-417`). The old empty-port `ECONNREFUSED` false control is gone.
- On a fully exercised direct-Git path with the sandbox removed, the hook connects and `:425-431` fails.

Why green still does not prove the claim:

- Missing bwrap prints `SKIPPED` and returns success (`:370-374`). `strict_available` only checks whether an absolute bwrap candidate exists (`shim_cli.rs:59-67`), not whether the full Strict capability set works.
- The inside assertion is `errno_for(..., "CONNECT") != Some(0)` (`:419-431`). Because `errno_for` returns `None` when no matching line exists (`:110-120`), a failed `socket()`, a hook that never executes, bwrap/shim refusal during commit, or any missing probe output passes. The test neither requires a `CONNECT` observation nor checks `run.commit_code`.
- It does not establish that `--unshare-net` caused the denial. Strict also emits `--net-deny` (`sandbox/mod.rs:567-579`); the shim handles TCP connect/bind and adds no port grant in that mode (`src/bin/gv-sandbox/main.rs:458-507`). Removing only the network namespace still leaves Landlock denial, and this assertion remains green. The comment at `escape_suite.rs:363-368` that the fresh namespace is the sole difference is false.
- Strict is not selected by current production policy.
- The test's pinned `PATH` and cleared environment omit the production process environment from the Strict composition it claims to exercise.

Minimum repair: make capability absence non-green; assert the hook and commit completed; require a present numeric `CONNECT` result and an explicitly justified errno; reject `SOCKET` and `None`; drive the production Strict configuration once dispatch exists. If the claim is specifically about bwrap's network namespace rather than composed Strict containment, add a negative control that removes only `--unshare-net` while preventing Landlock's independent TCP denial from masking that removal.

## Bottom line

C8's core lesson was provenance rather than liveness. The rewrite fixes provenance on parts of the happy audit path but still lets environmental absence become a passing test, still accepts generic/missing observations in two key checks, and tests a duplicate launcher under a more-hardened environment than production.

The milestone security claim therefore remains **unproven by this file**. The strongest result is the high-bit test's shim-level A/B; none of the five proves the complete production boundary required by C11.
