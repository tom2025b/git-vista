### `docs/adr/README.md` — a real conflict

Both sides appended to the ADR index. This branch added one row (0100); main
added four (0101, 0100, 0102, 0103).

**Resolved:** every one of main's rows kept verbatim, in main's own order, with

### `docs/adr/0100-*.md` — a collision git could not see

Not a conflict. Both sides added a file whose name begins `0100-`, but the
names differ, so git merged both happily and the repository ended with two
ADR 0100s. **This is the failure mode worth remembering: a semantic collision
in a numbering scheme is invisible to a textual merge.**

**Resolved:** this branch's ADR renamed to **0104** — `.md` and its tracked PDF
twin — with the title line and index row updated. 0104 was verified free by
listing `docs/adr/` on the merged tree, not inferred from the handoff, which
had also said 0104 (agreeing, but agreement is not verification).

**Verified by hand rather than trusted**, because a clean automerge of a file

## 2. Criterion 1 was genuinely partial, and is now genuinely closed

Cherry-pick was left out of the preview deliberately, and the branch said so in
two places, naming #596 as the blocker. #596 closed today via #599.

Two facts checked before writing any code — the handoff asserted both, and
citations in this repo have been wrong six times:

* **The engine really does preview a cherry-pick.**
  `crates/git-vista-server/src/preview.rs:758` maps
  `GitOperation::CherryPick` to `Previewable::CherryPick`. Three operations in,
  three mapped; the app mapped two.
* **#599 expected this panel to arrive.**
  `crates/git-vista/src/menu/commit_items.rs:237-243` says routing through
  `shell.open_confirm` "is what puts this operation in front of the confirm
  dialog's `/api/preview` panel (#594)", and defers two refusals to it: a pick
  already an ancestor of HEAD, and a merge commit. The halves were designed to
  meet.

**`onto` is dropped on purpose.** `OperationKind::CherryPick` carries the
destination the menu resolved, but the pick lands on whatever HEAD is checked
out when the server runs it, and the engine reads HEAD itself. A second copy of
the destination could only ever disagree with the operation it claims to
picture.

## 3. The move: a decision in a file that cannot be tested is not a decision

Criterion 1 has two halves. `previewable` (which subject earns a preview) was
already host-tested. `preview_subject` (which operation maps to which subject)
sat in `dialogs/confirm.rs`.

**CI compiles that file and lints it — `clippy -p git-vista --target wasm32`
and `trunk build` — and never executes it. This repo has no wasm test runner.**
Anything written there is unprovable by construction, which is the same shape
as the defect #594 exists to fix: `/api/preview` shipped registered,
contract-tested and wire-goldened, with no caller, and three audits missed it
because each checked a piece against its own contract.

So `preview_subject` moved to `features::dialogs::core`, and `confirm.rs` kept
only what needs a DOM. That is `confirm.rs`'s own stated rule, quoted from its
module doc:

> Which ceremony an operation gets, and every word either one shows, is decided
> in `features::dialogs::core` (pure, host-tested); this file is the part that
> needs a DOM.

### The belief that had kept it there was false

`DialogSubject`'s doc said `PendingOp` "lives in `crate::state`, which is
`#[cfg(target_arch = "wasm32")]`, so a decision written against it could never
be host-tested."

That describes the **re-export**, not the definition. `state.rs:113` is
`pub use crate::features::operations::kind::OperationKind as PendingOp`, and
`features/operations/mod.rs` declares `pub mod kind;` **ungated**. The type is
framework-free and host-compiled; `state.rs`'s own comment says it moved out of
`state` in M1.11 (#64) precisely so it could be unit-tested on the host, and
was re-exported under the old name so ~40 call sites kept reading naturally.

The doc is corrected rather than carried forward. **This is the second
misdirecting citation found today** — the first was `preview.rs:752-760`, which
the merge-down had made stale (the mapping is now at 753-766). Both are fixed
in the commits that touched them.

The corrected note keeps the reason that *is* still true: `DialogSubject` stays
a narrow vocabulary so the preview core never depends on the operations
vocabulary, and a new `OperationKind` variant cannot change what it decides.
The moved function takes `OperationKind` directly, never the wasm-only alias,
so the pure core does not reach into a wasm-only module.

## 4. Six mutations, six caught

Every one conclusive, against a clean working tree. Run key `gv-594-criterion1`.

| # | Target | Mutation | Verdict |
|---|---|---|---|
| 57 | `previewable` | CherryPick arm returns `None` | caught |
| 58 | `previewable` | CherryPick arm returns `RevertCommit` | caught |
| 59 | `preview_subject` | CherryPick arm deleted (falls to `_`) | caught |
| 60 | `preview_subject` | CherryPick arm returns `Revert` | caught |
| 61 | `preview_subject` | whole `Undo` arm returns `Revert` | caught |
| 62 | `preview_subject` | `_` returns `Merge { branch: "HEAD" }` | caught |

**The pair that matters is 58/60**, and the reason is a type coincidence:
`GitOperation::CherryPick` and `GitOperation::RevertCommit` each carry exactly
one `CommitOid`, and so do `DialogSubject::CherryPick` and
`DialogSubject::Revert`. Mapping one to the other **compiles, round-trips and
renders**. Mutation 60's failure output says it plainly:

```
left:  Revert     { commit: "bbbb…" }
right: CherryPick { commit: "bbbb…" }
```

Identical ids. Only the variant separates a picture of the operation from a
picture of its exact inverse. A test asserting on the commit id would have
passed straight through it, which is why both tests match on the variant.

Mutation 61 is the other one worth keeping: it reddened *two* tests — the seam
test and the positive revert case — and that asymmetry is what names the defect
rather than merely reporting one.

### The residual gap — now #612, not a footnote here

`confirm.rs` is still wasm-gated and still unexecuted by any test runner. What
moved is the **decision**; the wiring that calls it (`confirm.rs:100-105`) and
the panel that renders it remain there.

This is not a #594 problem and is no longer described here.
**It is [#612](https://github.com/tom2025b/git-vista/issues/612) — "Decision
logic can drift into wasm-only modules, where no test runner can reach it"** —
measured across the whole frontend: `main.rs:74-80` gates a dozen modules
behind `cfg(target_arch = "wasm32")` (activity, api, app, detail, dialogs,
menu, picker, render), and nothing executes any of them. The 58/60 mutation
pair in section 4 is cited there as the evidence: same oid, opposite
operation, an id-only assertion sails straight through.

**No browser assertion was added for the cherry-pick panel, deliberately.**
The panel's heading is outcome-dependent — "What this would do" only for a
`Picture`, otherwise "This would conflict" / "No picture for this one" /
"No preview here" — so an assertion on it would couple the test to whatever
the fixture's engine happens to answer that day. That is a test that passes
for the wrong reason, which is the failure this repo keeps paying for, and
today's browser leg had already produced two false greens. #612 is where this
gets solved properly, once rather than one spec at a time.

## 6. A false green, recorded because the next reader will hit it

`cargo test -p git-vista --lib` returns **`ok. 0 passed`** and exit 0.
`crates/git-vista/src/lib.rs` is one byte — an empty library. The crate is a
single `[[bin]]`, so `--lib` compiles nothing and truthfully passes nothing.

The correct invocation is `cargo test -p git-vista --bins`, which runs 804.

Caught only by reading the count instead of the word "ok". It is the same
family as this repo's standing caution — a green that proves nothing — and it
cost one wasted verification cycle.
