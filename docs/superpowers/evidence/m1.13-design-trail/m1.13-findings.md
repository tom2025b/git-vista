# M1.13 design — refutation findings to fix
All findings below were EMPIRICALLY TESTED by the refuting agent, not argued.

## Lens: attacker (verdict: needs-revision)
### [FATAL] §A.5 table: "diff.external — Closed — `-c diff.external=` on every diff-family spawn — [tested]", and the §A.3 config table which lists only `diff.external` and `diff.<name>.textconv` as the diff-side exec vectors. Also the reframed acceptance criterion in "The tension the facts file surfaces": "the set of config that can direct git to run anything is a fixed, explicit, server-authored list."
**Why it fails:** `diff.external` has a per-driver twin, `diff.<name>.command`, selected by a `diff=<name>` entry in `.gitattributes`. It is the *same* mechanism as `diff.external` but with a dynamic key name — precisely the property the design correctly identified for `diff.<name>.textconv` and then failed to generalize one row up its own table. A fixed `-c diff.external=` cannot enumerate it, and `--no-textconv` does not affect it (textconv and external-diff are different code paths). The design never mentions the key at all, so it is not in the "fixed, explicit, server-authored list" and is not in the §C test plan. The correct closure, `--no-ext-diff`, is name-independent, already supported on the diff family, and appears nowhere in the design.
**Tested scenario:** Tested, git 2.43.0, in `/tmp/.../scratchpad/atk/r2`. Repo has a tracked `.gitattributes` containing `* diff=pwn` and repo-local `diff.pwn.command = <script>`. I then ran the *exact* argv `diff_argv` builds for a merge commit (crates/git-vista-server/src/handlers/read.rs:597-614, `against_first_parent` branch), wrapped in the design's full hardened envelope: `env -i PATH=... GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_TERMINAL_PROMPT=0 GIT_PAGER=cat GIT_EDITOR=true git -c core.fsmonitor= -c diff.external= --no-pager diff --patch --no-color --no-textconv <parent> <head>`. Result: `PWN diff.<name>.command RAN argv=f.bin /tmp/git-blob-wQ9SyA/f.bin 626799f0... 100644 /tmp/git-blob-KD0iFX/f.bin 8c1384d8... 100644`. The script ran and its stdout replaced the patch the user sees. Re-running the identical command with `--no-ext-diff` added produced a real unified diff and no marker file. Reachability: read.rs:688 sets `against_first_parent = detail.parents.len() >= 2`, so `GET /api/diff/{oid}` for any merge commit is the trigger — a single unauthenticated-to-git-logic read endpoint. The other two vectors in the same array (`--name-status -z`, and the non-merge `show --format=` form) do NOT fire, which is why a casual test would miss this: only the merge/`diff` form runs external diff drivers by default.
**Prescribed fix:** Add `--no-ext-diff` to every diff-family spawn alongside the existing `--no-textconv`, and add a row for `diff.<name>.command` to the §A.3 and §A.5 tables with `--no-ext-diff` as the mechanism (name-independent flag, same class as `--no-textconv`, not the fixed-key `-c` class). Keep `-c diff.external=` as belt-and-braces. Add a §C real-git test `external_diff_driver_is_neutralized_regardless_of_driver_name`, built like the existing `textconv_is_neutralized_regardless_of_driver_name` (random driver name per run) but asserting against a **merge commit** so it exercises the `git diff A B` branch of `diff_argv` — a test written against the non-merge `show` form would pass vacuously. More importantly, treat this as evidence that hand-enumeration is the wrong primary defence and add a standing rule to §D: any config key whose name is dynamic (`.gitattributes`- or driver-selected) must be closed by a flag, not by `-c key=`, and the design must list which keys have that shape (`diff.<n>.command`, `diff.<n>.textconv`, `filter.<n>.clean/.smudge`).
### [SERIOUS] I5 table: "`GIT_TERMINAL_PROMPT=0` — No interactive credential/host-key prompt can ever be posed." And §B's pinned expected behaviour: "a push against a real HTTPS remote fails **fast** and **cleanly** … `fatal: could not read Username for 'https://github.com': terminal prompts disabled`", together with the §C test `push_without_reinjection_fails_fast_never_hangs`.
**Why it fails:** `core.askpass` is a repo-local-settable config key naming a program git executes to obtain credentials, and git consults it **before** the `GIT_TERMINAL_PROMPT` check. `GIT_TERMINAL_PROMPT=0` gates only the terminal fallback, not askpass. So the hardened envelope still executes an attacker-named binary on the push path, and the exact stderr string the design pins as its regression contract never appears. `core.askpass` is absent from every table in §A.3 and §A.5 and from the §C test list — another gap in the "fixed, explicit, server-authored list."
**Tested scenario:** Tested, git 2.43.0, in `/tmp/.../scratchpad/atk/r3`. Repo-local `.git/config` sets `core.askpass = <script>`; remote is `https://github.com/tom2025b/definitely-not-a-real-repo-xyz.git`. Command was the design's full policy: `env -i PATH=/usr/bin:/bin GIT_TERMINAL_PROMPT=0 GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_ALLOW_PROTOCOL=http:https:git GIT_EDITOR=true GIT_PAGER=cat git -c credential.helper= -c core.hooksPath=<pinned> --no-pager push origin HEAD`. The script ran: marker file contains `ASKPASS RAN prompt=Username for 'https://github.com':  pid=150405` plus a dump of its inherited environment. Git then used the script's stdout as the username. Note the two consequences: arbitrary code execution on the push path under the "hardened" policy, and the script also receives git's prompt text (which carries the target URL) and can write anywhere the server UID can. Adding `-c core.askpass=` to the same command produced no marker and the design's expected `fatal: could not read Username for 'https://github.com': terminal prompts disabled` — so the fix is one flag, and the design's own pinned message only holds once that flag exists.
**Prescribed fix:** Add `-c core.askpass=` to the forced-constants list in I5, unconditionally on every `SpawnClass` (not just Push — `fetch`-shaped and any future credential-touching command needs it too). `GIT_ASKPASS` and `SSH_ASKPASS` are already handled by `env_clear()`; state that explicitly rather than leaving it implicit. Add a §C real-git test `repo_local_askpass_is_never_executed` asserting the marker file is absent and that the failure text is exactly the terminal-prompts-disabled message — this makes `push_without_reinjection_fails_fast_never_hangs` non-vacuous, since today that test would pass on a repo with a hostile askpass only if the askpass happened to return garbage.
### [SERIOUS] The whole §A.3 scope table's "System scope: suppressed (NOSYSTEM) / Global scope: suppressed (GLOBAL=/dev/null)" column, and I13's argument that the clean/smudge gap is narrow because "`git lfs install` writes `filter.lfs.*` to the *global* config, which this design's `GIT_CONFIG_GLOBAL=/dev/null` already suppresses, so on a host with no OTHER means of setting it, the gap is arguably already closed as a side effect."
**Why it fails:** `include.path` (and `includeIf`) in repo-local config causes git to parse an arbitrary file as configuration, at repo-local precedence. `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` suppress the *default lookup paths* for those scopes; they do not prevent repo-local config from naming those same files (or any other file) explicitly. So "suppressed" in the design's table means "not loaded by default", not "unreachable" — and every conclusion the design draws from suppression, most sharply I13's "arguably already closed as a side effect," is conditional on the repo having no `include.path`. `include.path` appears nowhere in the design.
**Tested scenario:** Tested, git 2.43.0, in `/tmp/.../scratchpad/atk/r4`. I wrote `/tmp/.../atk/fakeglobal.conf` containing `[filter "lfs"] clean = ...` and `[core] askpass = ...` — standing in for the operator's real `~/.gitconfig`, which an attacker can name by absolute path (`/home/tom/.gitconfig`; the path is guessable and leaks in git-vista's own error text and clone destinations). Then repo-local `git config include.path <that file>`. Under `env -i PATH=... GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null`, `git config --get filter.lfs.clean` returned the value and `git config --get core.askpass` returned the script path — both from the "suppressed" file. `git add -A` with a tracked `.gitattributes` of `* filter=lfs` then invoked the imported clean filter (git reported `error: external filter '...' failed`, i.e. it executed it; my test value had a quoting bug so the payload itself errored, but the invocation is the finding). Combined with hole #2: a repo-local `include.path = /home/tom/.gitconfig` on this very box reinstates the operator's real `credential.https://github.com.helper = !/usr/bin/gh auth git-credential` for any spawn class where the design does *not* send the clearing `-c credential.helper=` — which per §B is Read, Mutate and Clone, i.e. every class except Push.
**Prescribed fix:** Three changes. (a) Add a row to §A.3 for `include.path`/`includeIf.*` stating plainly that they defeat scope suppression, and correct the table's "suppressed" wording to "not loaded by default; reachable via repo-local `include.path`." (b) Delete I13's "arguably already closed as a side effect" argument — it is false — and restate the clean/smudge gap at its true width. (c) Send the credential-helper clearing flag `-c credential.helper=` and `-c core.askpass=` on **every** SpawnClass, not only Push, since `include.path` means any class can find a helper. There is no `-c` that disables includes, so the residual must be named honestly in §D alongside clean/smudge. Add a §C test `repo_local_include_path_cannot_reinstate_a_credential_helper` that plants an `include.path` pointing at a file defining a hostile helper and asserts it never runs on a Read-class spawn.
### [SERIOUS] I8: "`core.hooksPath` is pinned to an explicit, chokepoint-computed path on every spawn: `-c core.hooksPath=<git-common-dir>/hooks` … This is what makes 'the permitted hook source is explicit and testable' concrete." Measured against Tom's binding Decision 2: "Repo-local hooks keep working; a client that silently skips a pre-commit hook is lying to the user."
**Why it fails:** Pinning `core.hooksPath` to `<common-dir>/hooks` does not merely block *hostile* redirects — it blocks *all* redirects, including the operator's own. `core.hooksPath` is the standard, repo-local mechanism by which husky, lefthook, pre-commit and every monorepo shared-hooks setup install hooks; `husky install` writes exactly `git config core.hooksPath .husky/_` into repo-local config. Under the pin, those hooks stop running and git-vista reports success. That is the precise failure Decision 2 forbids, and I8 does not acknowledge the trade-off, does not offer an allowlist/opt-in for an operator-declared hooks path, and §C contains no test that a legitimate `core.hooksPath` still fires. Secondary defect in the same invariant: `git rev-parse --git-common-dir` returns a **relative** path.
**Tested scenario:** Tested, git 2.43.0, in `/tmp/.../scratchpad/atk/r7`. Husky-shaped setup: `.husky/_/pre-commit` is `#!/bin/sh; echo "HUSKY PRE-COMMIT RAN" >&2; exit 1`, and repo-local `core.hooksPath = .husky/_`. Baseline, the operator's own git (`env -i PATH=... GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null git commit -m x`): prints `HUSKY PRE-COMMIT RAN`, exit 1, commit refused — correct. Under the design's pin (`git -c core.hooksPath="$(git rev-parse --git-common-dir)/hooks" commit -m x`): `1 file changed, 1 insertion(+)`, HEAD advances to the new commit, no hook output. The operator's veto was silently discarded and `/api/commit` would have returned 200. Separately, in the same test `git rev-parse --git-common-dir` printed `.git`, not an absolute path; `git rev-parse --path-format=absolute --git-common-dir` printed the full path. A naive `format!("{common_dir}/hooks")` therefore yields the relative `.git/hooks`, which git resolves against the git process's CWD — safe only because most sites pass `-C <repo>`, and `handlers/clone.rs:110-115` passes no `-C` at all.
**Prescribed fix:** Reframe I8 from "pin to the default" to "resolve, validate, then pin." Read the repo's effective `core.hooksPath`, resolve it, and pin to it if it canonicalizes to a path *inside the repository's own worktree or common dir*; pin to `<common-dir>/hooks` only when it resolves outside (the actual hostile case) — and when the design does override, say so in the response rather than silently succeeding, since Decision 2's whole point is not lying to the user. Whatever rule is chosen, it must be stated in I8 as an explicit trade-off, not omitted. Also switch the resolution to `git rev-parse --path-format=absolute --git-common-dir` and state that the pinned value is always absolute. Add two §C tests: `operator_configured_hooks_path_inside_the_repo_still_fires` (husky shape, asserts the pre-commit veto is honoured) and `hooks_path_pointing_outside_the_repo_is_overridden_and_reported`.
### [SERIOUS] I9 ("Every spawn carries a timeout") and I11 ("Cancellation reaches the whole process tree … cancel by writing to that cgroup's `cgroup.kill`"), plus the §C tests `hook_runtime_is_bounded_by_the_shared_envelope` and `hook_process_tree_is_fully_reaped_on_cancellation`, which assert only that the operation "fails/times out, never hangs" and that the grandchild's `/proc/<pid>` entry is gone.
**Why it fails:** The design introduces the first production kill path this codebase has ever had, and specifies nothing about the repository state a SIGKILL leaves behind. `git` cleans up `.git/index.lock` on SIGTERM/SIGINT via its atexit handler; `cgroup.kill` sends SIGKILL, which is uncatchable, so the lock file survives. `coordinator.rs:103-113` (`refuse_if_git_busy`) then returns HTTP 409 on the *mere existence* of `index.lock`, with no staleness check, no age check, no pid check — and `planner.rs:218` gates every mutating operation on it. A grep of the whole workspace for `index.lock` (crates/git-vista-server/src/coordinator.rs and two test suites only) shows nothing in production ever removes it. So one timeout kill converts a transient hang into a permanent, repository-wide refusal that only a human with shell access can clear. This is strictly worse than today's behaviour, where a hung git eventually finishes or is killed by a signal it can handle.
**Tested scenario:** Tested, git 2.43.0, in `/tmp/.../scratchpad/atk/r6`. Setup uses the design's own openly-accepted gap (I13, clean/smudge): repo-local `filter.slow.clean = <script that sleeps 60>` plus a tracked `.gitattributes` of `* filter=slow`. Ran `git -c core.fsmonitor= add -A` (the `StageAll` operation, `/api/stage`, `Mutate` class). After 2s: `.git/index.lock` HELD. I then SIGKILLed the whole tree — git and the filter — exactly as `cgroup.kill` would. Afterwards `pgrep -x git` is empty and `ls -l .git/index.lock` shows `-rw-rw-r-- 1 tom tom 0 … .git/index.lock` still present. From that moment `refuse_if_git_busy` returns `(409, "Another git process is working in this repository — wait for it to finish and try again.")` for every commit, stage, checkout, merge, rebase and push against that repository, forever. The attack is one HTTP request to `/api/stage` on a repo whose `.gitattributes` names a slow filter — a gap the design has already decided not to close. Note I also checked the commit-hook path (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-index-change` each sleeping 60s): git 2.43 holds no `index.lock` during those, so the commit path is clean — it is specifically the filter/`add` path that leaves the lock, which is why the accepted I13 gap and the new I9/I11 kill path compose into something neither is alone.
**Prescribed fix:** I9/I11 must specify post-kill reconciliation, and §C must test it. Concretely: after a timeout- or cap-triggered `cgroup.kill`, the chokepoint records which lock paths it may have orphaned (`<git-dir>/index.lock` at minimum; ref locks and `packed-refs.lock` for ref-touching classes) and removes exactly those, only for the repo it just killed, only when it owns the kill — never a blanket "delete any stale lock", which would race a legitimate external git. Alternatively, or additionally, escalate SIGTERM-to-all-in-cgroup with a short grace period *before* `cgroup.kill`, so git's own atexit cleanup gets a chance to run; state the grace period as a named parameter. Independently, `refuse_if_git_busy` should distinguish a live lock from a stale one (the design already resolves the git dir, so checking whether any process holds the repo is cheap) — but that is a fix to coordinator.rs, and this design is the thing that makes it load-bearing, so it belongs in scope. Add a §C test `a_killed_spawn_does_not_leave_the_repository_permanently_busy`: real repo, slow clean filter, short injected Mutate budget, assert the timeout is reported AND that a subsequent `/api/stage`-shaped call is not refused with 409.
### [MINOR] §A.6 table, first row: "`clone.rs:109` (`println!` of the raw clone URL) — Strip userinfo … applied at the chokepoint's own logging wrapper so `spawn_git`'s callers don't each need to remember it." And the closing sentence: "Applied at exactly two points: (1) the chokepoint's own log line …, and (2) the point where git's stderr is about to be written to either `eprintln!` or an HTTP response body."
**Why it fails:** `clone.rs:109` is not a chokepoint log line and cannot be reached by a chokepoint wrapper. It is a caller-side `println!` in the handler that executes *before* the spawn is constructed. A redaction function living inside `spawn_git` will never see it, so the raw URL — including any `user:token@` userinfo the operator pasted — still reaches stdout verbatim. The design names this as the leading secret sink and then assigns it a mitigation that structurally cannot apply to it.
**Tested scenario:** Read at crates/git-vista-server/src/handlers/clone.rs: `println!("[/api/clone] cloning {url} → {}", dest.display());` sits immediately above `let output = match tokio::process::Command::new("git").arg("clone").arg("--").arg(&url).arg(&dest).output().await`. A `POST /api/clone` with `https://ghp_realtoken@github.com/org/private.git` writes the token to the server's stdout — and per the project's own memory notes, that stdout is captured in `server.log` — regardless of any redaction added inside `spawn_git`. The design's own §C test `redact_url_strips_userinfo_from_log_and_response_sinks` asserts "neither the captured log line nor the HTTP error body contains the literal string `faketoken123`", so if that test is written honestly it will fail against the design as specified; if it only checks the chokepoint's own line, it passes while the leak remains.
**Prescribed fix:** Split the A.6 row: state that `clone.rs:109` requires an edit at the call site (wrap the URL in `redact_url(...)` there), not a chokepoint wrapper, and that `redact_url` therefore lives in a module both the handler and the chokepoint can call. Keep the chokepoint wrapper for the stderr/response sinks where it does apply. Make `redact_url_strips_userinfo_from_log_and_response_sinks` capture the process's actual stdout for the clone path, not just the chokepoint's tracing output, so it genuinely covers the sink it names.

### [FATAL] §A.2 environment table: "commit identity comes from repo-local config (user.name/user.email — [facts]), not $USER", used to justify omitting HOME from every SpawnClass except Push, and §B's claim that the only knowing regression is HTTPS push.
**Why it fails:** The [facts] file verified repo-local identity in *this* repo only. Tom's real identity is global: `git config --list --show-scope` shows `global file:/home/tom/.gitconfig user.name=tomb` and `user.email=thomaslane2025@gmail.com`. GIT_CONFIG_GLOBAL=/dev/null deletes it and env_clear() deletes the EMAIL fallback, so git falls through to gecos/hostname derivation and refuses. I counted the blast radius: of 21 git repos under /home/tom/projects, 9 have no repo-local user.email — countdown-timer, diskwatch, gluco, Link-Dump, memwatch-mcp, mind-map-mcp, printpdf-mcp, teacher-thing, toolbox-bridge. Several are repos CLAUDE.md names as active work. So commit through Git-Vista becomes a hard failure in 43% of his repos while the identical commit at his CLI succeeds. The error is made worse by the B3 verbatim-forwarding posture: stderr_stdout_or (planner.rs:1055-1066) ships git's full text to the iPad, and that text instructs the user to `git config --global user.email "you@example.com"` — advice that CANNOT work under this policy because global config is redirected to /dev/null, and that he has no shell to run from an iPad anyway.
**Tested scenario:** Tested in a temp repo with no repo-local identity: `env -i PATH=$PATH GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_TERMINAL_PROMPT=0 git commit -m x` → "Author identity unknown / *** Please tell me who you are. / Run git config --global user.email ... / fatal: unable to auto-detect email address (got 'tom@tom-hp-headless.(none)')". The same `git commit -m x` with the inherited environment succeeded and recorded `tomb <thomaslane2025@gmail.com>`. Operator path: Tom opens printpdf-mcp in Git-Vista on the iPad, taps Commit, and gets a wall of git text telling him to run a command that would not fix it.
**Prescribed fix:** Do not solve this by adding HOME to Mutate — that reintroduces the whole global-config surface the design exists to close. Instead resolve identity once, at server startup, with the *un*-hardened environment (`git -C <repo> config --get user.name` / `user.email`, or `git var GIT_AUTHOR_IDENT`) and carry it in the GitEnvPolicy that I6 already introduces, then inject it on Mutate spawns as `-c user.name=<v> -c user.email=<v>`. This makes the identity of a Git-Vista commit *identical by construction* to the one his CLI would write — which is the stronger answer to the identity question than either failing or diverging — and keeps the rest of global config suppressed. Add a test asserting a commit made through spawn_git in a repo with only global identity carries that global identity, and a second asserting repo-local identity still wins.
### [FATAL] I5 / §A.5: `GIT_ALLOW_PROTOCOL=http:https:git` forced on *every* spawn regardless of SpawnClass, listed in the A.5 table as "Closed, structurally" with the only named effect being refusal of the ssh transport.
**Why it fails:** GIT_ALLOW_PROTOCOL is an allowlist, so naming http/https/git silently *denies* the `file` transport — and git classifies a plain local filesystem path remote as the `file` transport, not just `file://` URLs. The design's A.5 table, §D, and the entire §C test list never mention this. It breaks the crate's own test suite: contract_suite.rs:405-425 (`push_branch_executes_through_the_pipeline`) creates a bare repo at a local path, does `remote add origin <dir>/remote.git`, and executes GitOperation::PushBranch through the pipeline; the other PushBranch cases at contract_suite.rs:199, :417 and :1012 have the same shape. Because I1 makes planner.rs's run_git (planner.rs:1023-1030) a thin caller of spawn_git and I5 forces the var unconditionally, those tests spawn `git push` with the file transport denied. `./dev gate` (dev:50) goes red on the crate's own suite, and the failure message gives no hint that an env var the chokepoint added is responsible.
**Tested scenario:** Tested: bare repo at $D/remote.git, work repo with `git remote add origin $D/remote.git`, then `env -i PATH=$PATH GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_TERMINAL_PROMPT=0 GIT_ALLOW_PROTOCOL=http:https:git git push origin main` → `fatal: transport 'file' not allowed`, exit 128. Same for `git clone $D/remote.git` and `git clone file://$D/remote.git`, both `fatal: transport 'file' not allowed`. Operator path beyond CI: any repo in his catalog whose origin is a local bare backup repo or a sibling worktree clone becomes un-pushable from the iPad, with an error string that names an environment variable he never set.
**Prescribed fix:** Set `GIT_ALLOW_PROTOCOL=http:https:git:file`. The design's stated goal for this variable is blocking ssh so core.sshCommand can never be consulted, and including `file` costs nothing against that goal — `file` invokes git's own upload-pack/receive-pack over a path, not a configurable external program. Add a regression test that pushes to a local bare remote *through spawn_git* (not raw git) and asserts success, so the collateral can never be reintroduced silently, alongside the existing ssh-refusal test.
### [SERIOUS] §A.4 I9/I11: a per-SpawnClass timeout (Mutate 30s) enforced by writing to cgroup.kill, presented as "one mechanism, no hook-specific branch of logic to get wrong," with §D listing nothing about post-kill repository state.
**Why it fails:** The design specifies how the process tree dies but not what the repository looks like afterwards. SIGKILL is not `git rebase --abort` — it leaves the operation half-applied. The codebase already knows this is unacceptable and says so in its own words at planner.rs:1484-1486: "A failed rebase (almost always conflicts) is `--abort`ed so a browser-only user is never left mid-rebase with no shell to fix it." exec_rebase honours that at planner.rs:1525 by running `rebase --abort` on a *non-zero exit*. A cgroup.kill'd rebase never reaches that branch — the process is gone. Worse, the wedge is not even detected: refuse_if_git_busy (coordinator.rs:103-113) tests only `git_dir.join("index.lock").exists()`, and a killed rebase leaves `.git/rebase-merge` with no index.lock, so the next request is accepted as if the repo were healthy. And there is no recovery operation to reach for: GitOperation (plan.rs:153-219) has CreateBranch, CommitOnHead, StageAll, CheckoutBranch, MergeBranch, PushBranch, RebaseOntoBase, RevertCommit, ResetTestRepo and friends — no AbortRebase, no AbortMerge.
**Tested scenario:** Tested: repo on `topic` three commits ahead of `main`, a post-checkout hook that sleeps 60s, `git rebase main` started under setsid and the whole group SIGKILL'd after 2s (the exact shape cgroup.kill produces). Result: `.git/rebase-merge` present, `git status --short --branch` reports `## HEAD (no branch)` — detached. index.lock absent, so refuse_if_git_busy would return None and admit the next request. A following `git add f; git commit -m after` succeeded on the detached HEAD, and `git checkout main` then printed "Warning: you are leaving 1 commit behind, not connected to any of your branches: fa40d53 after". From the iPad: rebase reports a timeout, the branch has not moved, the next commit appears to succeed but silently orphans itself, and nothing in the UI can run `git rebase --abort`.
**Prescribed fix:** Three parts, all cheap. (a) On any TimedOut/Capped outcome from a Mutate-class spawn, the chokepoint runs a bounded recovery spawn appropriate to the operation — `rebase --abort`, `merge --abort`, `revert --abort` — before returning the error, so the cgroup kill inherits exec_rebase's existing safety instead of bypassing it. (b) Widen refuse_if_git_busy (coordinator.rs:103-113) to also refuse on `rebase-merge`, `rebase-apply`, `MERGE_HEAD`, `CHERRY_PICK_HEAD` and `REVERT_HEAD`, with a message that names the state rather than saying "another git process is working." (c) Add the recovery to §C as a named test: kill a Mutate rebase past a short injected budget, then assert the repo is back on its original branch with no rebase-merge directory — that is the invariant planner.rs:1484-1486 already promises and the one this design currently breaks.
### [SERIOUS] §A.2 HOME row: "Every other SpawnClass — including Clone, whose URL a user pastes and which may carry its own embedded user:token@host userinfo, needing no helper at all — gets no HOME."
**Why it fails:** This assumes clone targets are public or that the operator will hand-embed a token. Neither holds. ### [FATAL] I11's recommended race-closure: "the spawned process raises SIGSTOP on itself immediately after fork (via CommandExt::pre_exec …), the parent migrates the now-stopped pid into its dedicated cgroup, then sends SIGCONT. This guarantees no descendant can be forked before the migration completes." (design §A.4, I11)
**Why it fails:** `std::process::Command::spawn()` (which `tokio::process::Command` wraps) creates a CLOEXEC error pipe before forking and then BLOCKS reading it until the child either execs (pipe closes on exec → EOF) or writes an errno. `pre_exec` runs in the child BEFORE exec. If the child SIGSTOPs itself there, the pipe never closes, so `spawn()` never returns — the parent never receives the pid, never migrates it, and never sends SIGCONT. Deadlock, not a race. The parent is wedged inside `spawn()`, so not even the timeout of I9 can fire (there is no future to time out yet — the block is synchronous inside tokio's spawn path).
**Tested scenario:** Tested. `/tmp/claude-1000/.../scratchpad/probe/stopprobe_crate` — `Command::new("/bin/true")` with `unsafe { cmd.pre_exec(|| { libc::raise(libc::SIGSTOP); Ok(()) }) }` then `cmd.spawn()`. Output: `calling spawn() with pre_exec that raises SIGSTOP ...` and nothing else; `timeout 8 ./target/debug/stopprobe_crate` → `EXIT=124`. The "spawn() RETURNED" line never prints. In production this means the very first `/api/commit` hangs the request task forever and leaks a stopped process.
**Prescribed fix:** Do the cgroup join from inside the child, not from the parent. Create the cgroup in the parent BEFORE spawn, open `<cg>/cgroup.procs` and keep the raw fd (clear CLOEXEC on it), then in `pre_exec` do a single async-signal-safe `write(fd, "0\n", 2)` — the child adds itself and execs immediately, no stop/cont, no window, and `spawn()` returns normally. Rewrite I11's closing paragraph around that, and add a named test `spawn_git_child_is_in_its_own_cgroup_before_exec` that reads `/proc/<child>/cgroup` and asserts the isolated path. Keep `CLONE_INTO_CGROUP` as the noted alternative.

### [SERIOUS] I8: the pinned path is "resolved via `git rev-parse --git-common-dir`" — and §C's hook tests are said to pin I8.

Interpolated verbatim into `-c core.hooksPath=`, git resolves the relative value against the worktree top-level, so from any non-top cwd it points outside the repo and NO hook fires — silently, exit 0. This is the same fail-open shape as the previous finding but reachable even in a repo with a perfectly normal `.git/hooks`. **Tested scenario:** Verified by classification. `durable.rs` has `#[cfg(test)]` at line 174 as an **inner block attribute inside the production fn `db_path()`**, at 456 as an **item attribute on a single fn** (`read_recovery_ref`), and at 487 on **`mod tests`**. In the other direction, `planner/coordination_suite.rs` (4 spawns), `planner/lifecycle_suite.rs` (2 spawns) and `planner/contract_suite.rs` (2 spawns) contain zero `#[cfg(test)]` for the module — the gate lives on the `mod` declarations at `planner.rs:1813-1822` — so any file-local grep reports 8 phantom production spawners and the test is red on a clean tree.
**Prescribed fix:** Drop the grep. Clippy's `disallowed_methods` is the real enforcement and I verified it works: a scratch crate with `clippy.toml` containing `{ path = "std::process::Command::new" }` and `{ path = "tokio::process::Command::new" }` produced `warning: use of a disallowed method 'std::process::Command::new'` and the same for `tokio::process::Command::new`, which under `./dev gate`'s existing `-D warnings` (`dev:50`) is a hard build failure. For the independent backstop, replace grep with the same trick `ci.yml`'s contract job already uses: assert the clippy config is *present and effective* by compiling a deliberately-bad snippet in a `trybuild`/`compile_fail` fixture, so the signal survives someone deleting `clippy.toml`.
### [MINOR] The implicit claim that the read path is unaffected — §B lists only push, and §D's exclusion list does not mention any change to read-side output.
**Why it fails:** `GIT_CONFIG_GLOBAL=/dev/null` also suppresses global `core.excludesFile`, so `worktree_status` (`handlers/read.rs:852`) begins reporting as untracked every file the operator has globally gitignored. That is a visible, user-facing change to the main status view, in the opposite direction from safe (it surfaces files the user deliberately hid, potentially including local secrets files matched by a global ignore).
**Tested scenario:** Tested. `$HOME/.gitconfig` with `core.excludesFile = ~/.gitignore_global` containing `notes.txt`, and a repo containing `notes.txt`. `HOME=$HOMEDIR git status --porcelain` → nothing for `notes.txt`. `env -i PATH=$PATH GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null git status --porcelain` → `?? notes.txt`.
**Prescribed fix:** Name it in §B as a third knowing consequence, and decide it deliberately: either accept it (the repo's own `.gitignore` is the only authority — defensible, and arguably more correct for a multi-user server) or forward a startup-resolved `core.excludesFile` as a server-authored `-c`. Either way add `worktree_status_ignore_semantics_are_repo_local_only` so the chosen behaviour is pinned rather than incidental.
### [MINOR] The blanket framing that the config-scope policy is settled by `GIT_CONFIG_NOSYSTEM=1` + `GIT_CONFIG_GLOBAL=/dev/null`, verified on git 2.43.0, with §C's real-git fixtures described as reproducible without any stated version floor.
**Why it fails:** The policy fails OPEN on an older git, and fails open silently. `GIT_CONFIG_GLOBAL` is a comparatively recent addition; a git that does not know it simply ignores it — git treats unrecognised environment variables and even a non-existent config path as a no-op rather than an error. On such a host, global config is fully visible, the entire A.3 table is void, and — critically — most of §C stays green, because the hook tests assert only that the *hostile* marker is absent, which is satisfied when `-c core.hooksPath` wins regardless of whether global suppression worked at all. `--path-format=absolute` (needed per the earlier finding) and `cgroup.kill` (kernel ≥5.14) add two more silent floors. `ci.yml` pins the Rust toolchain via `dtolnay/rust-toolchain@stable` but takes whatever git `ubuntu-latest` happens to ship, and that drifts.
**Tested scenario:** Tested the fail-open shape directly on 2.43.0: `GIT_CONFIG_GLOBAL_TYPO=/dev/null git status --porcelain` → `rc=0`, no diagnostic; `GIT_CONFIG_GLOBAL=/nope/nothere git status --porcelain` → `rc=0`, no diagnostic. So neither a version that predates the variable nor a typo in the variable name produces any signal at all — the suppression just does not happen.
**Prescribed fix:** Add a startup assertion, not just documentation: run one probe at server start — plant a sentinel key in a temp file, point `GIT_CONFIG_GLOBAL` at it, and confirm `git config --get` does NOT see it — and refuse to start (or log loudly and degrade) if suppression is not actually in effect. Mirror it as `global_config_suppression_is_actually_effective_on_this_git` in §C, plus an explicit minimum-git-version constant checked in the same place, so an old-git host is loud rather than quietly unhardened.

## Survey surprises
- GIT_TERMINAL_PROMPT and GIT_EDITOR ARE already set in production — main.rs:124-125 (`std::env::set_var("GIT_TERMINAL_PROMPT", "0")`, `std::env::set_var("GIT_EDITOR", "true")`), directly contradicting the task prompt's stated codebase fact ('no env_clear, no GIT_TERMINAL_PROMPT, no GIT_PAGER, no GIT_EDITOR anywhere in production'). They're set process-wide once in main(), not per-Command, so every one of the 9 spawn sites inherits them today incidentally. GIT_PAGER genuinely is absent, but is empirically moot — see filter_surface's core.pager test.
- There are 9 production git spawn sites, not 8: `durable.rs:416-438` (`write_recovery_ref`, spawn at durable.rs:425, `git update-ref refs/git-vista/recovery/<id> <oid>`) is production code with no `#[cfg(test)]` guard and was not included in the task prompt's count of 'git_cmd.rs (5), planner.rs (1), handlers/read.rs (1), handlers/clone.rs (1), coordinator.rs (1)'. Verified by grepping every `process::Command::new("git")` in the server crate and checking each against surrounding `#[cfg(test)]` boundaries.
- tokio::process::Command::output() inherits the parent's stdin by default; std::process::Command::output() does not. Confirmed with two matching harnesses (a live never-EOF FIFO as stdin, 5s timeout): the std version returned in <1ms with empty output, the tokio version blocked past the full 5s timeout (rc=124). Of the 9 production spawn sites, only `git_stdout_capped` (git_cmd.rs:137, `.stdin(Stdio::null())`) explicitly nulls stdin — the other 8 all use bare `tokio::process::Command` with no stdin config and therefore silently inherit whatever the server process's own stdin happens to be. GIT_TERMINAL_PROMPT=0/GIT_EDITOR=true cover the *known* interactive prompts, but not this generic inherited-stdin hang vector, whose real-world risk depends entirely on how the server process is launched — exactly the kind of incidental-environment dependency Decision 1 is trying to eliminate for env vars, and the same principle should extend to stdin.
- core.fsmonitor set in repo-local .git/config is a full command-execution vector that fires on plain `git status` and `git add -A` — the two most routine calls in the app — and survives `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null`. The facts file's hooksPath-pinning trick (`-c core.hooksPath=<explicit>`) does nothing to stop this; it's a completely separate config key requiring its own explicit override on every invocation. This is arguably a bigger day-one hole than the hooks surface Decision 2 already names, because it needs no commit/checkout/merge action at all, just a status poll.
- setsid inside a hook defeats process-group-based cancellation outright, confirmed empirically (see process_tree_findings) — so 'spawn git in its own process group and killpg on cancel' is not, by itself, an adequate fix for Decision 2's 'cancellation with process-TREE cleanup' requirement.
- A fast-forward merge and a true (diverged-history) merge commit fire different hook sets, and neither one fires post-commit: FF = {post-merge, reference-transaction}; real merge commit = {pre-merge-commit, commit-msg, post-merge, reference-transaction}. Both were tested cleanly (setup commits isolated from the operation under test) and both results were reproducible.
- Non-interactive `git rebase`'s replayed commits do NOT fire pre-commit or commit-msg — tested twice on a clean, non-conflicting replay. Only pre-rebase (once, at the start), post-checkout, post-commit (once, at the end) and post-rewrite fire. A design that assumes 'rebase re-runs the commit hooks for every replayed commit' would be wrong and would over- or under-budget accordingly.

## Non-hook execution surface

Tested empirically in throwaway temp repos, git 2.43.0. Every one of these fires from REPO-LOCAL `.git/config` and survives `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null` — the same suppression trick the facts file validated for core.hooksPath does NOT touch any of these; each is a distinct config key that needs its own neutralization.

1. clean/smudge filters (.gitattributes + `filter.<name>.clean`/`.smudge` in repo-local config): clean fires on `git add`/`git commit`, smudge fires on `git checkout`. Tested end-to-end with a filter defined only in repo-local config (`git config filter.noisy.clean/.smudge ...`, no --global) — fired on add, fired again on commit, fired on checkout, and still fired with NOSYSTEM+GLOBAL=/dev/null set. The filter *program* can never come from a tracked file (git's own security design), so a bare `git clone` of an untrusted repo cannot inject a *new* filter program via .gitattributes alone — but a locally pre-configured filter name (e.g. git-lfs's `filter.lfs.*`, which `git lfs install` writes to the operator's *global* config) means ANY repo whose tracked .gitattributes references that name will invoke it, including a hostile clone — this is a live, conditional risk on any host with git-lfs (or similar) globally configured, not tested further this session.

2. core.fsmonitor: the single sharpest finding of this task. Set to an arbitrary shell command in repo-local .git/config, it is executed by `git status` AND `git add -A` — both tested, both fired, both survived NOSYSTEM+GLOBAL=/dev/null. This is worse than the filter case because it needs no .gitattributes at all and fires on read-only status polling (handlers/read.rs:848-878, worktree_status) and on StageAll (planner.rs:1286-1299) — two of the most frequently-hit code paths in the app. `-c core.hooksPath=<explicit>` (the facts file's mechanism) does nothing against this; it needs its own override, e.g. `-c core.fsmonitor=` on every invocation.

3. diff.external: repo-local `diff.external` fires on `git diff` — tested, fired, survived suppression.

4. textconv: `.gitattributes` `diff=<name>` + repo-local `diff.<name>.textconv` fires on `git diff` for matching paths — tested, fired (twice, once per diff side), survived suppression. Same two-part mechanism as clean/smudge: attribute names the driver, config supplies the program, so the same clone-time caveat applies (name must already be configured locally to be exploitable via a hostile .gitattributes).

5. core.sshCommand: tested — did NOT fire on `git status` (a command that never dials a transport). This one is transport-gated: it only runs when git actually opens an ssh:// or git@ connection. Since this repo's remote is HTTPS (verified-facts.md) and `validate_clone_url` (protocol/dto.rs:217-237) accepts only http(s)://\|git://, git-vista's own clone flow can never trigger it — but an operator-added repo whose *pre-existing* origin remote is ssh:// would still be exposed if any push/fetch-like operation dialed it, since core.sshCommand is repo-local-config-driven just like the others.

6. core.pager: tested with a repo-local pager script and stdout redirected to a plain file (non-tty) — the pager script did NOT run. This substantiates that every production spawn site's piped/`.output()`-captured stdout already defeats the pager by git's own tty auto-detection, independent of any GIT_PAGER env var. Acceptance criterion "pager... prompts cannot hang" is therefore already empirically true for the current call shape — the gap is making that structural (e.g. also setting GIT_PAGER=cat / passing --no-pager) rather than incidental to always using piped stdio.

Net for Decision 2 design: pinning core.hooksPath via `-c` closes the hooks vector the facts file already proved, but leaves core.fsmonitor, clean/smudge, diff.external and textconv completely open — none of those are hooks in the githooks(5) sense, so a hooks-only design is not sufficient for "hardened environment" per the binding decision.

## Process-tree findings

Tested directly with a tokio harness matching production's spawn shape (`kill_on_drop(true)`, piped stdio, `.kill().await` + `.wait().await` — the exact two-call sequence `collect_child_stdout_capped` uses on a cap hit, git_cmd.rs:191-193/197). Fixture: a `pre-commit` hook (.git/hooks/pre-commit) that (a) writes its own pid to a file, (b) backgrounds a `setsid`'d grandchild loop that appends a timestamp to a heartbeat file every 200ms and is fully disowned/detached from stdio, then (c) itself sleeps 30s so the outer `git commit` process stays alive to be killed mid-hook.

Result, in order: git pid captured (116702); after 1.5s, hook pid confirmed alive (116703, child of git) and heartbeat log already had 8 lines. Killed only the git child via `.kill().await` + `.wait().await` (the production cancellation shape) and reaped it — `/proc/116702` gone immediately, confirmed. One second later: the hook process (116703) was STILL ALIVE (`/proc/116703` exists = true) despite its parent (git) being dead and reaped. The heartbeat file kept growing after the kill (13 lines immediately after, 18 lines one second later) — the setsid'd grandchild was never touched at all. `ps` after cleanup showed the grandchild (pid 116704) with `sid=116704` — its own, brand-new session, distinct from git's/the hook's original session, and `ppid=1` (already reparented to init).

Conclusions: `kill_on_drop(true)` (and the equivalent manual `.kill()+.wait()`) only ever signals the single, direct child PID tokio holds a handle to. It has zero effect on that child's own children — a hook, and anything the hook itself forks, survive a killed git process as ordinary orphans. This is a structural gap, not a bug: nothing in `git_cmd.rs`'s current cancellation path (or any of the 9 production spawn sites) asks the kernel for tree-wide cleanup at all today.

What would actually close it, and why the obvious answer isn't enough: putting git in its own process group at spawn (Command::process_group / a pre_exec setsid call) and calling `killpg` on cancellation is the standard fix, but it is NOT sufficient here, because the test fixture's grandchild called `setsid` itself and thereby escaped into an entirely new session/process-group — confirmed directly in the `ps` output above (`sid=116704`, not the group git/the hook started in). Any hook — malicious or merely badly written — can defeat a process-group-based kill the same way with one line. `PR_SET_PDEATHSIG` is also insufficient on its own: it is a per-process opt-in that only binds one specific child to one specific parent's death and does not cascade to further descendants, especially ones that themselves call `setsid` (which, per Linux semantics, also clears any inherited death-signal disposition for the new session leader). The only mechanism that reliably catches a self-detaching subtree regardless of how many times it forks or calls setsid is a Linux cgroup: putting the git invocation (and everything it ever spawns, by cgroup inheritance rather than pgid/session membership) into its own cgroup and writing to `cgroup.kill` (kernel ≥5.14) or SIGKILL-ing every pid under `cgroup.procs` kills the whole tree unconditionally, because cgroup membership is inherited across fork/exec/setsid alike and cannot be escaped without CAP_SYS_ADMIN-class privilege the hook won't have.
