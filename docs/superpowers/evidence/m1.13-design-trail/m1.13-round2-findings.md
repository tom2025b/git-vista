# Round-2 refutation findings (design v2)
All empirically tested. Verdicts: both lenses needs-revision.

## Lens attacker — needs-revision

### Previously-fatal STILL OPEN
- core.hooksPath blind pin breaks repo-local hook setups (husky/lefthook/pre-commit) — Decision 2 violation. Fix B's *shape* is right, but step 2 prescribes the wrong base for a relative value, so the canonical husky case still ends in a pin under which no hook fires, exit 0, and — because the mis-resolved path lands inside the common dir — the predicate reports 'inside the repo' so no warning is surfaced either. See new hole #1; tested in /tmp/.../scratchpad/atk2/t1.sh.

### New holes

#### [FATAL] §A.3 I10 step 2: “Resolve it to an absolute path with `--path-format=absolute --git-common-dir` as the base for a relative value”, plus step 3’s predicate “inside the repository’s own worktree or common dir” and the closing claim “This keeps repo-local hooks working (Decision 2).”
**Why:** Git resolves a relative `core.hooksPath` against the **worktree top-level**, not the common dir — the design’s own quoted [tested] note says exactly that (“a relative value resolves against the worktree top-level”) and then prescribes the common dir as the base one clause later. For the canonical husky value `.husky/_` the two bases differ: worktree-top gives `<repo>/.husky/_` (hook fires), common-dir gives `<repo>/.git/.husky/_` (nothing there). Worse, the mis-resolved path is *inside the common dir*, so step 3’s predicate returns “inside the repo” → HONOURED → pinned, with **no warning**, which is the branch Decision 2 exists to make impossible. v1 killed husky loudly-in-principle; v2 kills it while reporting success and passing its own safety check.

**Tested:** Tested, git 2.43.0, /tmp/claude-1000/-home-tom-projects-Git-Vista/74d494cf-.../scratchpad/atk2/t1.sh. Repo with `.husky/_/pre-commit` (echoes HUSKY FIRED) and repo-local `core.hooksPath=.husky/_`. Baseline under the hardened env: `HUSKY FIRED`, commit proceeds. COMMON=`…/r1/.git`, TOP=`…/r1`, effective hooksPath=`.husky/_`. Design as written — `git -c core.hooksPath="$COMMON/.husky/_" commit -m c2` → `[main a8103dd] c2`, **zero hook output**, HEAD advanced. Correct base — `git -c core.hooksPath="$TOP/.husky/_" commit -m c3` → `HUSKY FIRED`, then the commit. Same repo, same envelope, only the base differs.

**Fix:** Change step 2 to: resolve a relative effective `core.hooksPath` against the **worktree top-level** (`git rev-parse --path-format=absolute --show-toplevel`); use `--path-format=absolute --git-common-dir` only to compute the *fallback* target `<common-dir>/hooks` and as one of the two containment roots in step 3. State the bare-repo case (no worktree → only the common dir is a valid root). Make `repo_local_hookspath_inside_the_worktree_is_honoured` assert the hook’s marker/veto is actually observed (a positive assertion), and add a companion asserting that a `.husky/_`-shaped value is pinned to `<toplevel>/.husky/_`, not `<common-dir>/.husky/_` — as written the §C test name would pass against a fire-nothing pin only if written carelessly, so pin the resolved string too.

#### [FATAL] §A.3 I7’s `GIT_ALLOW_PROTOCOL=http:https:git:file` row: “`file` invokes git’s own upload-pack/receive-pack over a path, **not a configurable external program**, so including it costs nothing against the actual goal.” Also §B item 3 (“Closed by including `file`”) and the standing rule in I9 that dynamic-name keys must be closed by a flag.
**Why:** That sentence is empirically false. Over the `file` transport git executes the receive-pack/upload-pack program **named by repo-local config** — `remote.<name>.receivepack` on push and `remote.<name>.uploadpack` on fetch. Under v1’s `http:https:git` the vector was structurally unreachable (`fatal: transport 'file' not allowed`, nothing ran); v2 re-enabled `file` to unbreak `contract_suite.rs`, and in doing so opened arbitrary local code execution on the shipped Push path (`exec_push`, planner.rs:1419-1423, `["push", remote]`). The remote *name* is repo-chosen, so this is a **dynamic-name key** — by the design’s own standing rule it cannot be closed with `-c key=`, and it appears in no table, no §D gap list and no §C test.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t6.sh. Repo with `origin` = a local bare repo, repo-local `remote.origin.receivepack=<script>` and `remote.origin.uploadpack=<script>`. Under v2’s exact env (`GIT_ALLOW_PROTOCOL=http:https:git:file`, NOSYSTEM, GLOBAL=/dev/null, TERMINAL_PROMPT=0) plus `-c core.askpass= -c credential.helper= -c core.fsmonitor=`: push → marker `RECEIVEPACK PROGRAM RAN args=…/bare.git`; fetch → marker `UPLOADPACK PROGRAM RAN args=…/bare.git`. Same push under v1’s value → `fatal: transport 'file' not allowed`, marker NONE. Closure verified in the same run: `git push --receive-pack=git-receive-pack origin main` → marker NONE and the push succeeded normally.

**Fix:** Add `--receive-pack=git-receive-pack` to every Push-class argv and `--upload-pack=git-upload-pack` to any fetch/ls-remote-shaped argv (name-independent flags, exactly the class the standing rule demands), add `remote.<name>.receivepack`/`.uploadpack` as rows in the §A.3 and §A.6 tables and as the fourth and fifth members of the dynamic-name list, delete the false “not a configurable external program” clause from the `GIT_ALLOW_PROTOCOL` row, and add §C test `local_transport_receivepack_override_is_neutralized` (repo-local `remote.origin.receivepack` marker script, Push class to a local bare remote, assert marker absent and push succeeds) — it composes directly with the already-planned `push_to_a_local_path_remote_succeeds_through_spawn_git` fixture.

#### [FATAL] §A.2’s GPG row (“`GPG_TTY`, `GNUPGHOME` — **No**. No signing operation ships.”) and the acceptance criterion in “The tension the facts file surfaces”: the set of config that can direct git to run something is “either (a) a fixed key name the chokepoint always overrides with `-c key=`, (b) a dynamic key name closed with a name-independent flag, or (c) a named, tested, still-open gap — never an unenumerated surface.”
**Why:** The design reasoned about signing at the *environment* layer and concluded no GPG variables are needed — then never asked whether repo-local **config** can turn signing on and name the program. It can: `commit.gpgsign=true` + `gpg.program=<anything>` executes an arbitrary binary on every `git commit`, i.e. on `GitOperation::CommitOnHead` (plan.rs:158), the single most-used Mutate operation. Neither key is in any §A.3/§A.6 table, §D gap list or §C test — a fourth unenumerated exec surface, in the same class as the `core.askpass` miss that v1 was faulted for. It also has a sub-key twin that defeats the obvious patch: `gpg.format=ssh` routes to `gpg.ssh.program`, so `-c gpg.program=` alone does not close it.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t2.sh and t3.sh. (t2) repo-local `commit.gpgsign=true`, `gpg.program=<script>`; under the full v2 envelope (`env -i PATH=… GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_TERMINAL_PROMPT=0 git -c core.askpass= -c credential.helper= -c core.fsmonitor= -c diff.external= -c core.hooksPath=… commit -m x`) → marker `GPG-PROGRAM RAN args=--status-fd=2 -bsau t <t@t>`. (t3) same repo with `gpg.format=ssh` + `gpg.ssh.program=<script>`, adding the naive `-c gpg.program=` → marker `SSH-SIGN PROGRAM RAN args=-Y sign -n git -f /dev/null /tmp/.git_signing_buffer_tmp…`, i.e. still executed. Adding `-c commit.gpgsign=false` instead → no marker, commit succeeds.

**Fix:** Force `-c commit.gpgsign=false` (and `-c tag.gpgsign=false` if any tag operation is ever added) on every Mutate spawn — close the **enabler**, not the program keys, because the program key name varies with `gpg.format`. Add a row to §A.3/§A.6 (`commit.gpgsign` + `gpg.program`/`gpg.<fmt>.program`, fixed-name enabler, dynamic-ish program key) and a §C test `repo_local_signing_config_never_executes_a_signing_program` covering both the openpgp and `gpg.format=ssh` shapes. If a later milestone ships signing, that ADR flips this constant and adds the env, per §D’s widening procedure.

#### [SERIOUS] §A.3’s standing rule enumerating the dynamic-name category: “`diff.<n>.command`, `diff.<n>.textconv`, and `filter.<n>.clean`/`.smudge` are **the three known members** of the dynamic-name category as of this design.”
**Why:** `merge.<driver>.driver` is a fourth, selected by `merge=<name>` in tracked `.gitattributes` exactly like the textconv/clean pair, and it executes on `git merge`, `git rebase` and `git revert` — three shipped GitOperations (`MergeBranch` plan.rs:181, `RebaseOntoBase` plan.rs:197, `RevertCommit` plan.rs:212). It is strictly more consequential than the clean/smudge gap the design does name, because the merge driver writes the merged file content that then gets committed: it doesn’t just run code, it decides what lands in the repository. There is no `--no-ext-merge` flag, so it is unclosable by the design’s own two mechanisms and must be a named gap.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t4.sh. Repo with tracked `.gitattributes` = `* merge=pwn`, repo-local `merge.pwn.driver = <script> %A %O %B`, divergent `main`/`topic`. Under the full v2 envelope: `git … merge topic -m m` → `Merge made by the 'ort' strategy` **and** marker `MERGE DRIVER RAN args=.merge_file_2CVRMo .merge_file_lOytba .merge_file_AMFRnT`; the script’s output became the merged file. Repeating with `git … rebase topic` → `Successfully rebased` **and** a second `MERGE DRIVER RAN` marker. Both under `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null` with `-c core.askpass= -c credential.helper= -c core.fsmonitor= -c diff.external= -c core.hooksPath=…`.

**Fix:** Add `merge.<name>.driver` as the fourth member of the dynamic-name list and as a row in §A.6 marked **Open — documented gap**, alongside `filter.*`, with its true blast radius stated (it controls committed content on merge/rebase/revert, not just execution). Same reachability caveat as clean/smudge applies (the driver must already be configured locally; `.gitattributes` only names it) and should be stated the same way. Add §C test `custom_merge_driver_gap_is_pinned_and_visible` so the accepted gap is a chosen behaviour rather than an omission, and mention it in §D.

#### [SERIOUS] §A.3 I10 step 3 + I4’s caching: “Canonicalize the resolved path and check whether it lies inside the repository’s own worktree or common dir … still blocks the actual threat (a redirect resolving outside the repo)”, with the resolved decision “cached per repo path in shared state so a `Bootstrap` round only happens once per repo per server lifetime.”
**Why:** The predicate validates a *path string* at Bootstrap time; git re-resolves that path — following symlinks — at every later exec. Nothing binds the validated canonical target to the path that is subsequently pinned, and I4 makes the validate→exec window last the whole server lifetime. Because Fix B’s whole point is that the honoured hooks directory lives in the **worktree**, its contents are tracked, checkout-switchable data, not `.git/config` — so I9’s “operator trusts the repo’s `.git/config`” argument does not cover it. A branch that replaces the tracked hooks directory with a tracked symlink pointing outside the repo turns the cached, ‘validated-as-inside’ pin into execution of code from an arbitrary filesystem location, exit 0, no warning.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t7.sh (bare mechanism) and t8.sh (reachable via shipped operations). t8: repo with operator-set repo-local `core.hooksPath=githooks` and a tracked `githooks/pre-commit`; Bootstrap validates `readlink -f <top>/githooks == <top>/githooks` → inside → pinned. Branch `attacker` commits `githooks` as a **tracked symlink** to `/tmp/.../evil`. Then, using the *cached* pin on every spawn: `git -c core.hooksPath=$PIN checkout attacker` → OK; `git -c core.hooksPath=$PIN add -A`; `git -c core.hooksPath=$PIN commit -m after` → stderr `HOOK FROM OUTSIDE THE REPO RAN`, marker file `PWNED`, commit succeeds. Both steps are shipped GitOperations (`CheckoutBranch` plan.rs:178, `CommitOnHead` plan.rs:158) over plain HTTP.

**Fix:** State plainly that the containment check is a TOCTOU-bounded check, then bound it: (a) re-resolve and re-validate the hooksPath immediately before each Mutate/Push spawn rather than caching the decision for the server lifetime (it is one `Bootstrap` `rev-parse`/`config --get`, already the cheapest class), or (b) require the honoured path to contain no symlinked component (compare the lexically-joined path against `canonicalize`) and re-check that property per spawn, or (c) invalidate the cache on any operation that can rewrite the worktree (checkout, merge, rebase, revert, reset, stage). Also specify what happens when `canonicalize` fails (path absent): it must fall to the override-plus-warning branch, not to the raw value. Add §C test `hookspath_that_becomes_an_outward_symlink_after_validation_is_not_honoured`.

#### [SERIOUS] §A.2’s HOME row (“**Yes, `Push` and `Clone`** … no shipped capability on those classes touches a credential store” for the others) composed with I14 (“Hardened environment reaches hooks for free … a local-operator-trust question (I9), not a gap in this design”) and I10’s decision to honour worktree-resident hooks.
**Why:** v2 changed two things at once and did not check the composition: hooks may now come from **tracked worktree content** (I10), and `HOME` plus a working credential helper are now present on **Push and Clone** (v1 gave HOME to Push only and pinned hooks to the untracked `.git/hooks`). A `pre-push` hook is a child of the Push-class git process, so it inherits `HOME=/home/tom` and can simply read `~/.config/gh/hosts.yml` or run `gh auth token` — the operator’s real GitHub PAT — from a script that arrived with a `git checkout`. I14 waves this off as covered by I9, but I9’s stated trust boundary is the repository’s `.git/config`, not its tracked files, and §B’s regression list never names it.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t10.sh. Repo with repo-local `core.hooksPath=githooks` (honoured by I10) and a **tracked** `githooks/pre-push`. Pushed with the exact Push-class envelope (`env -i PATH=… HOME=$HOME GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null GIT_TERMINAL_PROMPT=0 GIT_EDITOR=true GIT_PAGER=cat GIT_ALLOW_PROTOCOL=http:https:git:file git -c core.askpass= -c credential.helper= -c 'credential.helper=!/usr/bin/gh auth git-credential' -c core.hooksPath=<top>/githooks -c core.fsmonitor= push origin main`). Push succeeded; the hook recorded `HOME=/home/tom`, `gh token readable: YES`, and the full `GIT_CONFIG_PARAMETERS` including the injected helper. Separately confirmed `env -i PATH=/usr/bin:/bin HOME=$HOME sh -c '/usr/bin/gh auth token'` returns a live token (masked in the transcript), so PATH+HOME is sufficient for exfiltration.

**Fix:** Name it in §B as a regression the design knowingly ships (it is the price of Decision 2 × private-repo auth), and prefer bounding it: resolve the credential **out of band** at the chokepoint — run `git credential fill` (or the resolved helper) as its own `Bootstrap`-class spawn that carries HOME and dispatches no hooks, then hand the resulting credential to the Push/Clone spawn through a tiny server-authored helper that echoes a value read from an inherited fd, so the git process that runs hooks never carries `HOME` at all. If that is deferred, say so in §D and add §C test `push_class_hook_environment_carries_no_credential_store_path` (denylist assertion on `HOME`/`XDG_CONFIG_HOME` in a real `pre-push` hook’s env) so the choice is pinned either way.

#### [SERIOUS] §A.3 I7’s `GIT_ALLOW_PROTOCOL=http:https:git:file` (keeping `git`) together with the `core.sshCommand` row: “**Closed, structurally** — `GIT_ALLOW_PROTOCOL` refuses the ssh transport before this key is ever consulted.”
**Why:** `core.gitProxy` is the exact analogue of `core.sshCommand` for the `git://` transport — a repo-local config key naming a program git executes to open the connection — and `git` is *in* the allowlist (and `validate_clone_url` explicitly accepts `git://`, git-vista-protocol/src/dto.rs:227). The design enumerated the ssh twin and closed it by transport denial, then left the git:// twin both enabled and unenumerated. Unlike every other key in the table it is **not closeable by `-c`**: I tested both the empty value and the documented `none` value and the proxy program ran anyway; only removing `git` from the transport allowlist stops it.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t7.sh (§F) and t9.sh. Repo with repo-local `core.gitProxy=<script>` and remote `git://127.0.0.1:9418/nope.git`. Under v2’s env with `-c core.askpass= -c credential.helper=`: `git ls-remote gp` → marker `GITPROXY RAN args=127.0.0.1 9418`. Retried with `-c core.gitProxy=` → marker still written. Retried with `-c core.gitProxy=none` → marker still written. Retried with `GIT_ALLOW_PROTOCOL=http:https:file` (no `git`) → `fatal: transport 'git' not allowed`, marker NONE.

**Fix:** Drop `git` from `GIT_ALLOW_PROTOCOL` (`http:https:file`) and correspondingly drop `git://` from `validate_clone_url`’s `ALLOWED` (dto.rs:227) — it is a plaintext, unauthenticated, effectively dead transport for a catalog server whose own remote is HTTPS, and removing it is the only mechanism that closes `core.gitProxy`. Add the `core.gitProxy` row to §A.3/§A.6 with “no `-c` closure exists — closed only by transport denial (tested: empty and `none` both fail)”, add §C test `git_transport_is_refused_so_core_gitproxy_is_never_consulted`, and note the `validate_clone_url` change as a deliberate, user-visible narrowing in §B.

#### [SERIOUS] §A.2 I5: “The startup value itself is resolved once, at server start, with the process’s *actual* environment (not `env_clear()`’d): `git config --get user.name` / `--get user.email` … This makes a Git-Vista commit in a repo with only global identity **identical by construction** to what his CLI would have written there.”
**Why:** `git config --get user.name` is repository-context-sensitive: run inside a repository it returns that repository’s **repo-local** value, not the global one. The server’s cwd is a repository — Git-Vista’s own checkout, which has repo-local identity — so the “global identity” captured at startup is actually Git-Vista’s repo-local identity, and it is then stamped on commits made in every catalog repo that lacks local identity: precisely the 43% of repos FIX A exists to serve. The commits are misattributed by construction, in the opposite direction from the design’s headline claim, and nothing in §C would catch it (the two identity tests both build their own `GitEnvPolicy` from a fixture value and never exercise the resolution step itself).

**Tested:** Measured on the real box, no writes. From `/home/tom/projects/Git-Vista` (where `./gv serve` runs): `git config --get user.name` → `tom2025b`, `--get user.email` → `262510778+tom2025b@users.noreply.github.com` — identical to `git config --local --get`. From `/tmp`: `tomb` / `thomaslane2025@gmail.com`. So a commit Git-Vista makes in, say, `printpdf-mcp` (one of the 9 identity-less repos the finding enumerated) would be authored `tom2025b <…noreply…>`, while the same commit at his CLI in that directory is authored `tomb <thomaslane2025@gmail.com>`.

**Fix:** Specify the resolution context, not just the environment: run the startup probe with cwd set to a directory that is **not** inside any repository (a `tempfile::tempdir()`), or read the scopes explicitly (`git config --global --get …` with a `--system` fallback), and assert at startup that the resolved value did not come from a repo-local file. Add §C test `startup_identity_resolution_is_not_taken_from_the_servers_own_repository` (temp “global” config + a server cwd inside a repo carrying a different local identity; assert the global one is what `GitEnvPolicy` holds).

#### [MINOR] §A.2 I5’s probe: “`-c user.name=<startup>` is added to a `Mutate` spawn’s argv **only when `git config --local --get user.name` … reports absent**”, supporting “repo-local wins **by construction**.”
**Why:** `--local --get` reads only the repo-local *file*; it does not see values a repo-local `include.path` pulls in, even though those values are what git actually commits with. So a repository whose identity is supplied through an include is probed as “absent”, the startup identity is injected, and `-c` (which the design itself proved always wins) overrides the identity the CLI would have used. This is the same `include.path` mechanism the design elsewhere treats as a first-class threat, applied to the one place v2 chose `--local` specifically to get scope-precision.

**Tested:** Tested, git 2.43.0, /tmp/.../scratchpad/atk2/t8.sh (§J). Repo with only `include.path = <file>` in `.git/config`, the included file setting `user.name = IncludedName` / `user.email = included@example.com`. Under `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null`: `git config --local --get user.name` → nothing, rc=1 (probe says ABSENT → design injects). `git config --get user.name` → `IncludedName`, rc=0. A plain commit records `IncludedName <included@example.com>` — i.e. the value the injection would have overridden.

**Fix:** Use the hardened-environment effective read as the probe instead of `--local`: `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null git config --get user.name`, which returns exactly “what this repository provides once system and global are suppressed”, includes and all — the property the design actually wants. Update I5’s text and add the include shape as a case in `repo_local_identity_wins_over_the_injected_startup_value`.

#### [MINOR] §A.4 I16: “`spawn_git` `debug_assert!`s that `diff_family: true` is only ever paired with `args[0]` in a fixed, enumerated set … This makes the flag set a property the type system carries, not a runtime string match the chokepoint has to keep in sync with every future caller.”
**Why:** The assertion is one-directional. It catches `diff_family: true` with a non-diff subcommand (a loud failure the author would hit immediately), and says nothing about `diff_family: false` with a diff-family subcommand — the silent, fail-open direction, in which `--no-textconv`/`--no-ext-diff` are simply omitted and the exact vector the v2 revision was written to close reopens for that caller. The type does not in fact “decide”: a caller still has to remember a boolean, and `false` is the stated default. This is the same “the map will rot” objection the design quotes and claims to have answered.

**Tested:** Design-level, no test needed to state it, but the reachable shape is concrete: `handlers/read.rs`’s `diff_argv` has three branches (read.rs:597-614) and the merge branch is the one that fires `diff.<n>.command`. A future fourth branch, or a refactor that routes a `git diff`/`git log -p` through a helper defaulting `diff_family` to `false`, produces an ext-diff-enabled spawn with no compile error, no `debug_assert`, and no failing test — §C’s two driver tests exercise only the call sites that were already correct.

**Fix:** Make the assert bidirectional: `debug_assert!(diff_family == DIFF_FAMILY.contains(args[0]))`, so a diff-family subcommand spawned without the flag fails as loudly as the inverse. Better still, drop the boolean and derive it in the chokepoint from a `Subcommand` enum the caller must name — then it genuinely is the type deciding. Either way add the §C test the operator lens asked for and v2 dropped: enumerate every subcommand string the crate actually spawns and assert each is classified, so the classification cannot silently fall out of date.

#### [MINOR] §A.4 I13: “create the cgroup in the parent **before** calling `spawn()` … write to the cgroup’s `cgroup.kill`.”
**Why:** The design specifies creation and killing but never teardown, and a cgroup directory persists until `rmdir`. Every spawn — including the `Read`-class `worktree_status` poll the iPad session issues continuously and the extra `Bootstrap` spawns v2 adds — creates one kernel object that is never reclaimed. Nothing in §A, §C or §D mentions removing it, and `rmdir` is only legal once the subtree is empty and reaped, so the ordering has to be designed rather than assumed. On an 8 GB host this is an unauthenticated-request-driven kernel-memory growth path.

**Tested:** Read of the full §A.4/§A.5 text: `cgroup.procs`, `cgroup.kill` and the delegation probe’s own “create and immediately remove a throwaway subtree” all appear; no per-spawn removal does. A status-polling client at, say, 1 Hz over an 8-hour session leaves ~29k live cgroup directories under the server’s delegated subtree, none removable by anything in the design.

**Fix:** Add one line to I13: the per-spawn cgroup is removed (`rmdir`) after the child is reaped, on every exit path including timeout/cap/error, with the removal itself failure-tolerant and logged; note that `rmdir` requires the subtree to be empty so it must follow the final `wait`. Add §C test `spawn_git_removes_its_per_spawn_cgroup_after_the_child_is_reaped` (count subtree entries before and after N spawns, including one timed-out spawn).

## Lens verifier — needs-revision

### Previously-fatal STILL OPEN
- core.hooksPath blind pin breaking husky/lefthook (FIX B) — the pin is no longer blind, but the prescribed relative-value resolution base is wrong, so husky/lefthook still silently skip, now without even the warning the design promises
- Commit identity for repos with only global identity (FIX A) — the per-field conditional-injection mechanism is correct and I re-verified it, but the startup resolution step is unscoped and picks up the server's OWN repo-local identity, so the injected author is wrong in exactly the 43% of the catalog the fix was written for

### New holes

#### [FATAL] §A.4/I13: "create the cgroup in the parent before calling spawn(), open <cg>/cgroup.procs and keep the raw fd across the fork (clear its CLOEXEC flag), then in pre_exec perform a single async-signal-safe write(fd, \"0\\n\", 2)" — and the mermaid at line 500, "create cgroup, open cgroup.procs, keep fd (CLOEXEC cleared)".
**Why:** Clearing CLOEXEC is (a) unnecessary and (b) a privilege leak into untrusted code. fork() preserves file descriptors regardless of FD_CLOEXEC — CLOEXEC only takes effect at execve, which happens AFTER the pre_exec write. Clearing it therefore buys nothing and instead leaks a WRITABLE handle on <cg>/cgroup.procs into the git process and into every hook git dispatches. A repo-local hook can enumerate /proc/self/fd, find that handle, and write the git-vista SERVER's own pid into it, migrating the server into the very cgroup the chokepoint is about to cgroup.kill. The timeout path then SIGKILLs the whole server. This converts the new bounded-runtime feature into a whole-process kill primitive reachable from one HTTP request against a repo with a hostile pre-commit hook — strictly worse than today, where a hung hook only wedges one request.

**Tested:** Tested, two probe binaries at /tmp/claude-1000/-home-tom-projects-Git-Vista/74d494cf-ac3e-4ae7-bd7e-f3451291e0f2/scratchpad/cgprobe (kernel 7.0.0-28-generic, cgroup v2, delegated user scope).
